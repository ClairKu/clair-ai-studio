CLAIR · 且慢 AI 交易研究
结论机构案例首期范围技术路径路线图证据
Qieman · AI Trading Capability Study · 2026.09.15

让一句话变成
可确认的交易

这件事值得做，但项目定义必须克制：不是让大模型自主决定买什么，而是让 AI 把用户已表达的交易意图，编排成一笔规则正确、信息完整、可审计、由用户最终确认的订单。

公开证据调研8 个机构/模式自营 App 内闭环用户强确认不构成投资建议
ONE-LINE DECISION做“AI 交易协助”，暂不做“AI 自主交易”。

模型负责理解和解释；规则服务负责校验；且慢交易系统负责接收指令与执行；用户对每笔真实订单负责最终确认。

01 · PRODUCT DECISION

先把“AI 下单”说清楚

行业里最容易犯的错，是把“自然语言入口”“AI 推荐”“订单生成”“自动执行”混成一个概念。且慢应主动拆开责任。

MODEL

大模型可以做

识别用户意图、补齐缺失字段、调用只读事实、解释费用与失败原因、生成结构化订单草稿。

RULE ENGINE

规则系统必须做

实名、账户、适当性、产品可售、额度、支付、截止时间、重复单、风险与合规预检。

USER

用户必须做

在且慢自营交易页面查看最终不可变订单，完成显式确认和强认证；模型不能替用户确认。

NEVER

第一阶段不做

AI 自选产品、自定金额、自择时、代输交易密码、无人确认报单、把“可能成功”说成“已成交”。

一个硬设计决定：模型工具集中不提供 submit_order。模型只能创建带有效期的订单草稿；真实提交由且慢 App 的确认组件触发，与当次用户认证和不可变订单摘要绑定。
02 · CONTROLLED LOOP

目标态不是一句话直达交易所

它是一条七段式受控链路。大模型只占前两段的一部分，交易核心仍是确定性系统。

01 INTENT理解意图动作、产品、金额、账户、时间
02 GROUND拉取事实持仓、余额、产品、规则、时间戳
03 PREFLIGHT交易预检适当性、可售、限额、支付、重复单
04 DRAFT锁定草稿order_draft_id + TTL + 摘要哈希
05 CONFIRM用户确认自营页展示、强认证、一次性授权
06 EXECUTE交易核心执行幂等提交、受理回执、状态机
07 WRITEBACK结果写回成功/失败/在途/退款与下一步
判断：且慢真正要建设的不是一个“下单 Prompt”，而是交易意图协议、预检服务、订单草稿、确认令牌、执行状态机、审计证据链六项平台能力。

04 · MVP SCOPE

首期只打穿“一买一查”

先证明模型能可靠地把一笔明确交易变成正确草稿，并在失败后说清楚原因。范围扩大之前，必须先把零事故门槛跑出来。

IN · MUST BUILD

一期包含

  • 已登录用户购买一只明确指定的、已上架投顾策略/组合
  • 用户自己给出金额；AI 只做澄清，不替用户决定金额
  • 完整交易前检查并解释每个阻断原因
  • 生成有时效、不可变、可撤销的订单草稿
  • 跳转且慢自营确认页，展示费用、支付方式、风险和预计处理时间
  • 查询订单状态并用交易系统事实解释失败/在途
OUT · DO NOT BUILD YET

一期排除

  • “你帮我选一个”“现在该买什么”等 AI 自主选品与择时
  • 长赢、复杂跟车、跨账户转账、赎回再买、组合级换仓
  • 自动输入密码、人脸/生物信息或把凭据传给模型
  • 外部大模型客户端内直接签约、测评、付款或报单
  • 定时/条件触发后无人确认的开放式自动交易
  • 模型根据聊天推断“已经成功”，而不查询交易状态
ACCEPTANCE A

“我想买周周同行 2 万元”

系统识别对象与金额 → 拉取账户/产品事实 → 预检 → 返回唯一草稿；若缺支付方式，只追问必要问题。

ACCEPTANCE B

“为什么我买不了？”

只引用规则系统返回的阻断码，明确是风险测评、余额、银行卡限额、开放状态还是资格问题，并给正确入口。

ACCEPTANCE C

“昨天那笔失败了吗？”

用 order_id 查询真实状态；区分受理、扣款、确认份额、失败、退款，不把“已受理”说成“已成交”。

05 · REQUIREMENT CONTRACT

要补的不是一个接口，而是六个契约

这六项能同时约束产品、研发、交易、合规和数据团队，也是未来接入千问、ChatGPT 等外部 Agent 时的安全边界。

01 INTENT SCHEMA

交易意图协议

action、product_id、amount、account_id、payment_method、schedule、source_utterance、confidence；金额与产品不可由模型暗填。

02 PREFLIGHT

交易前检查

统一返回 pass / block / need_user_action、阻断码、可解释文案、修复入口、数据时间戳。

03 DRAFT

订单草稿

draft_id、摘要哈希、费用/风险快照、expires_at。任何字段变化都使旧确认失效。

04 CONFIRMATION

确认令牌

绑定 user、device、draft、认证级别、确认时间和一次性 nonce；防重放、防串单。

05 STATE MACHINE

执行状态机

draft → awaiting_confirmation → submitted → accepted → processing → success / failed / refunded / canceled。

06 EVIDENCE

审计证据链

原始话术、解析结果、事实版本、规则决策、确认画面、最终 payload、回执、模型/提示词版本与 trace_id。

06 · TOOL BOUNDARY

把危险能力放到模型拿不到的地方

模型越强，权限边界越要简单。最安全的实现不是“写一个更严的 Prompt”，而是架构上让模型无法绕过确认门。

✓ get_trade_context()

只读账户、产品、余额、规则和状态；字段最小化、按需授权。

✓ precheck_order(intent)

确定性预检；模型只能解释返回结果，不能覆盖规则。

✓ create_order_draft(intent)

创建短时有效草稿；记录摘要哈希和幂等键。

✓ get_order_status(order_id)

事实查询；所有“成功/失败”文案必须有状态响应。

✕ submit_order(payload)

不得作为模型工具；由 App 确认组件与交易网关直接调用。

✕ get_password / biometric

认证凭据绝不进入模型上下文、日志或第三方 Agent。

07 · DELIVERY ROADMAP

12 周走到小流量真实订单

时间是建议窗口，不是现有承诺。每一阶段都有“继续 / 收缩 / 停止”门，不以 Demo 演示代替真实证据。

第 0–2 周
契约与影子模式

冻结意图 schema、状态机和红线；用脱敏历史话术离线回放，不创建真实订单。

出口：字段准确率、边界测试、风险评审

第 3–6 周
沙箱纵切

一只明确策略 + 明确金额；跑通预检、草稿、确认模拟、失败恢复和全链审计。

出口：100% 可回放的 Demo 与故障注入

第 7–10 周
员工/白名单真单

仅且慢 App、自营确认页、限额、可撤销、人工值守；先从极小范围真实订单验证。

出口：零越权、零重复、零状态幻觉

第 11–12 周
1% 灰度

扩大到符合条件用户；A/B 对比交易准备时长、阻断修复率、完成率和投诉。

出口：Go / Pivot / Stop 决策
🛡️
安全门槛（必须为零）未确认提交、重复订单、跨用户串单、凭据入模、虚构交易状态、绕过适当性。
🎯
质量门槛（建议目标）关键字段精确匹配 ≥99.9%；高风险意图 100% 拦截/转人工；交易状态事实一致率 100%。
📈
业务假设（需 A/B 验证）交易准备时长下降 40%–60%；可修复阻断的完成率相对提升 10%–20%；不预设 AUM 结果。
08 · REGULATORY BOUNDARY

为什么一定要在且慢自营 App 内完成

监管要求把“谁接收客户交易指令、谁做销售和适当性、谁承担责任”钉得很清楚。外部大模型适合做入口和草稿，不适合作为真实交易终点。

SELF-OPERATED SYSTEM

交易指令由自营系统直接接收

中基协《网上基金销售信息系统技术指引》要求基金销售机构通过自身运营管理的信息系统直接接收投资者交易指令，并记录接收时间。

THIRD-PARTY LIMIT

外部平台只能转接

2026 年 9 月 30 日起施行的新规要求第三方平台在购买环节跳转金融机构自营平台，且不得介入签约、资金划转、适当性等销售环节。

HUMAN IN THE LOOP

核心决策需要人工复核

基金业协会大模型应用规范强调权限审计、日志追溯，并建议生成内容作为辅助、经人工复核；涉及交易执行代码不得全自动生成上线。

因此，面向千问、ChatGPT、Claude 等外部 Agent 的且慢 MCP，首期最多开放“查询 + 预检 + 创建行动草稿 + 拉起且慢 App”；签约、测评、支付、确认和报单必须回到且慢自营环境。这里是产品与合规共同评审建议，不替代正式法律意见。
