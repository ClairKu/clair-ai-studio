01 · Executive judgment

该保留什么，必须重做什么

真正的产品价值不在页面数量，而在“系统发现重要时刻后，帮助顾问安全地把服务做完”。

值得保留：AI 已经进入作业流，而不是漂浮在旁边

  • 任务、客户、资料、报告与 AI 共享上下文，页签式工作区适合复杂顾问作业。
  • 大额赎回、购房用款、配置偏离、年度检视等场景贴近真实服务时刻。
  • “先核实事实、不主动挽留、不承诺收益、顾问确认后再写回”体现了正确的人机边界。
  • 任务具备来源、优先级、状态、判断依据和关闭原因，已经有案例化运营底座。

必须重做：从演示壳升级为可信作业系统

  • AI、报告、数据源和系统连接目前均为本地模拟，不能按“已接入”验收。
  • 同一页面体系出现客户数、日期、任务内容等真相冲突，影响管理决策可信度。
  • 权限只到菜单可见，缺少客户归属、字段、动作、工具和审计层的控制。
  • 生成报告、写资料、改任务等高风险动作尚无统一预览、审批、落库和回滚协议。

04 · Issue register

不是继续加页面，而是先清掉这些风险

P0 阻断可信试点；P1 决定产品效率；P2 影响规模化与体验质量。

P0

统一数据真相缺失

首页“服务客户数 44 / 在管 11”，看板“管户客户数 128 / 在管 121”；同一 Demo 还出现 2028–2029 服务日期与 2026 场景混用。

管理者会先质疑数据，后续所有 AI 判断与经营指标都失去信任基础。

数据产品 + 后端
1 周内
P0

AI 只模拟，不是真连接

无真实远程调用；路由由关键词判断，回复来自本地模板，700ms 后显示。模型下拉只是字符串列表。

无法评估时延、幻觉、权限、成本、工具调用成功率和故障降级。

AI 平台
V1.3 前
P0

“完全访问”一键授权过粗

权限主要是菜单可见；AI 端一个开关就允许改待办、替换洞察或写资料，缺少对象、字段、动作、工具、时效和审批维度。

不满足客户数据隔离、最小权限、敏感动作确认和事后追责。

安全 + 合规
2 周内
P0

证据语义没有贯穿所有 AI 输出

部分客户对象区分事实 / 推断 / 未知，但 AI 画像、市场洞察、风险分和建议没有逐条来源、口径、时间、置信度与复核状态。

顾问容易把推断对客说成事实；管理者无法追查某次建议基于哪一版数据。

产品 + 算法
2 周内
P0

写回与回滚协议不完整

任务关闭、报告生成、文件上传、分享等行为多数只改内存或提示文案；刷新后状态可能消失，外部流程未触发。

无法证明“顾问完成了一项服务”，也无法在误操作后恢复。

若移动端不是目标，应明确“仅桌面”；若要跨端，不能靠补丁修复，需重做布局模式。

1

首页：今日服务驾驶舱

只回答三件事：今天必须服务谁、为什么、下一步怎么完成。经营指标下沉到看板，不抢任务决策的注意力。

2

客户 360：决策证据页

所有摘要逐条绑定数据源、时间、口径与状态；把“我知道什么 / 我推测什么 / 还缺什么”固定成页面骨架。

3

AI：受控执行协议

每次动作先生成不可变草稿，展示影响对象与差异，顾问强确认后由业务系统执行，再回写状态和审计记录。

06 · Roadmap

三阶段推进，先闭环再平台化

不建议继续横向补齐 7 个域。先把 3 条高频、高价值、高风险链路做深。

V1.3 · 0–4 周

可信闭环 Demo

  • 清洗成一套可追溯演示数据，统一日期与全局口径。
  • 只保留资金异动、配置偏离、定期检视三条黄金链路。
  • 接入至少一个真实模型网关，工具仍可用沙盒。
  • 补齐事实 / 规则 / 推断 / 未知的统一呈现。
  • 建报告工作坊最小闭环：预览、编辑、复核、归档。
验收刷新后状态可恢复；所有动作有草稿、确认、结果和审计。
验收3 条链路各完成 10 个真实顾问脚本测试，无占位数据。
Pilot · 5–10 周

小范围生产试点

  • 连接客户、持仓、交易、适当性和服务记录的只读数据。
  • 启用对象级权限、租户隔离、脱敏和审计。
  • 开放任务写回与报告归档；对客发送仍需人工确认。
  • 做 10–20 位顾问灰度，建立人工兜底与问题升级。
  • 按任务类型做模型评估，不用“整体满意度”掩盖风险。
验收数据新鲜度、信号准确率、任务 SLA、证据覆盖率达到阈值。
验收无越权访问、无自动对客发送、关键动作 100% 可回放。
V2.0 · 11–20 周

平台化与规模运营

  • 上线技能注册、版本、依赖、权限、评测与审批体系。
  • 模型路由按任务质量 / 成本 / 时延选择，而非让顾问挑模型名。
  • 扩展服务机会、团队运营和多机构配置。
  • 形成报告模板市场、规则市场与可观测性平台。
  • 在有实验设计时评估业务结果，不把相关性叫 AI 增量。
验收每个技能都有负责人、测试集、版本、风险级别和回滚版本。
验收业务指标、人工编辑率、错误类型和模型成本可按场景追踪。
07 · Acceptance & metrics

验收不能只看“能不能点”

每条链路都需要数据、决策、动作、结果四类指标；业务结果需与因果归因分开。

建议立即做

  • 把 44 / 128 等冲突全部收敛为同一 fixture 与口径服务。
  • 首页首屏只保留“必须处理的 3–5 件事”。
  • 把“模型名称”换成“快速 / 深度 / 合规优先”等任务策略。
  • 每个 AI 输出附一键查看证据与差异。
  • 所有写动作先显示影响范围和回滚点。

建议暂缓

  • 暂缓扩充 Agent / Skill / CLI 数量与市场运营。
  • 暂缓对客自动发送、自动改客户事实、自动结案。
  • 暂缓把经营净流入变化归因给 AI。
  • 暂缓移动端“硬压缩”；先确定移动端只做提醒还是完整作业。
  • 暂缓用更多仪表盘掩盖核心服务链路没有闭环。
08 · Golden flows

下一版只需要赢下三条链路

每条都必须从真实事件开始，到可验证结果结束。

A

未知原因大额资金变动

交易事实 → 已知计划比对 → 创建任务 → 先问用途 → 记录事实 → 判断是否需要规划 → 约定下一步。验收重点：不挽留、不推销、不把推断写成事实。

B

配置偏离与风险复核

持仓变化 → 适当性规则 → 偏离原因假设 → 顾问核实 → 客户意愿 → 是否启动再平衡。验收重点：基准、风险分、阈值和例外都可解释。

C

定期检视与报告交付

到期提醒 → 数据冻结 → 报告草稿 → 顾问编辑 → 合规复核 → 客户沟通 → 结论与后续任务回写。验收重点：文档版本、发送对象、结果和承诺可追溯。

最终建议：做减法，换可信度

V1.2 已经证明“AI 深度融入顾问工作流”的方向可行。下一步不应继续证明页面能做多少，而要证明三件事：数据是真的、建议说得清、动作收得回来。

保留：任务 × 客户 × AI 融合强化：证据与状态机重做：权限与写回协议暂缓：技能生态扩张
