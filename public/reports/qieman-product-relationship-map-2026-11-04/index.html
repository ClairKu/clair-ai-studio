先抽象业务，再映射实现

根问题：如何持续理解客户诉求、承担明确服务责任，并通过可接续的专业行动与证据完成服务？

业务过程、能力分解、对象关系、应用实现、技术供给、项目变更是不同视图；不能拼成一棵包含树。

一、先纠正原词的维度

原词所属维度
客户服务业务总域或服务职能
私域渠道与关系方式
VIP客群 / 权益层级
顾问运营组织与运营职能

一位VIP客户可在企微沟通，由顾问承担服务、运营负责准备、小顾接续结论。这些维度可以同时成立，不应各建一套客户或任务模型。

类型定义例子 / 边界

业务对象业务中维护或处理的实体与记录客户、目标、权益、服务实例、任务、回执
业务事件已经发生且有证据的事实变化客户提交请求、测评到期；事件不是系统
洞察 / 判断候选解释 / 有责任主体的裁决可能有用款需求 / 决定先确认期限

三、只使用有含义的关系

关系类型连接什么约束
分解业务能力 → 子能力同类型能力可有层级；不是把产品、事件与项目串成树
处理 / 引用业务能力 → 业务对象对象是被处理或引用的内容，不是能力的下一级名称
支持 / 承载应用系统 → 业务能力多对多；专业判断与签发由指定责任角色承担，应用提供支持
记录 / 投影台账 → 各域权威对象统一查询与证据；原域仍维护各自事实与状态
规范 / 约束标准服务能力包 → 服务执行规范定义如何合格完成，不包含客户当前进度
实例化服务定义 / 规范 → 客户服务实例实例绑定客户、诉求、承诺、责任与完成条件
形成工作服务实例 → 业务任务任务具有当前责任人、期限、状态与完成证据
触发评估事件 / 洞察 → 策略判断 → 服务或任务可以忽略、静默或补证；并非每个事件都派单
组织 / 支持业务流程组织活动与任务；任务可由人工或多次技术运行支持业务任务与技术运行不是固定包含链，纯人工任务同样成立
产生证据授权动作 → 交付物 / 回执 → 完成评价生成、审核、发送、送达、解决分别记录
供给平台实现 → 能力契约 → 消费应用平台供给是一种关系；接口、权限、版本、时效与支持必须明确
改变 / 交付项目或工作包 → 目标能力 / 应用 / 规范项目不进入在线运行调用链
标注建设状态 / 协作方式 → 被建设对象已有、升级、新建是状态；共建是可叠加的协作方式

四、“台账”和“包”各自是什么

名称类型定义
客户服务台账记录视图按客户关联各域事实、服务状态、判断与交付证据；写入回归权威域。
标准服务能力包版本化规范定义服务目标、适用条件、方法与工具、角色责任、标准交付、异常和评测；供AI与真人复用。
任务运行包授权快照引用服务实例与任务并装配必要状态快照、有效授权约束摘要；不持有权威状态、不授予新权限；动作执行时重新校验有效授权、来源、版本与时效。

本蓝图默认服务包指标准服务能力包。客户服务套餐是权益组合，客户服务实例是履约实体，任务运行包是当次输入；四者分别建模。

五、业务对象与技术运行分开

长期服务关系可以产生多次客户服务实例；一次具体服务可跨多个会话、任务和渠道。业务流程可组织多个任务；任务可纯人工完成，也可由一个或多个技术运行支持。Agent重试属于技术运行，不应重复创建业务服务或误标服务完成。

事件描述发生了什么，洞察解释可能意味着什么，判断决定是否处理，任务落实由谁做什么。客户请求、周期履约和顾问判断也能创建任务；不必把一切工作包装成事件。
