A · 基本信息与业务价值

团队与责任

产品设计牵头，研发、测试、数据及对应业务协作；人员与投入待确认

背景与立项判断

需求并行增加后，写周报的成本只是表层问题，更大的损耗是未结束项目长期没有记录、上周推进项本周消失，以及计划日期被误当成实际完成。应让系统负责事实核对和状态治理，产品负责人保留优先级与资源取舍。

C · 拟建闭环与人工边界

首期作业边界

首期限定一个团队的一张需求池及其关联Jira。完成为可直接使用的事实周报与待确认队列送达；不自动改变业务优先级、不承诺研发排期、不因聊天中的“好了”自动标结案。

01 / 拟建步骤周度时间自动触发
02 / 拟建步骤锁定数据快照与关联关系
03 / 拟建步骤核对状态 证据和时间
04 / 拟建步骤生成进展 停滞 冲突清单
05 / 拟建步骤交付事实周报及核实任务
06 / 拟建步骤回执归档和下周期续跟踪
常规：证据齐全 → 按规则直接交付异常：缺证 / 冲突 / 超时 / 越权 → 保留状态、转责任队列

最终交给谁、完成是什么

团队负责人收到本周实质进展、上周有动作本周无更新、长期停滞、阻塞依赖和下周已确认计划；每项含需求ID、证据链接、数据时点与责任人。无证据显示未知，不能补写故事。

规则与判断依据

人工确认状态字段权威顺序和停滞阈值。已部署、已验收、已关闭分开，不能互相推导。计划变更须引批准记录；来源矛盾转owner，超时升级。周报发布仅在指定内部位置，不自动群发给未授权对象。

异常不能自动消失

分支系统动作结果状态与责任
输入缺失 / 事实冲突保留快照并请求最小补证；有限重试待补证；业务负责人确认
权限失败 / 系统断连停止写入；告警并排队恢复执行失败；平台接管，不记通过
敏感 / 高风险 / 规则外带理由分流，禁止硬输出或擅自操作人工队列；专业责任人裁定
交付无回执 / 无人接单按SLA升级，保留开放状态未完成；接收方负责人处理
抽检发现错误 / 已误关闭重开任务、回溯受影响交付、暂停该规则不合格；从自动成功分子回扣

D · 所需资源、缺口与可行性

必须先补的依赖

关联ID、权威状态、时间快照、内部交付回执

基础设施支持

需求池与Jira只读、批准评审记录限定读取、飞书指定台账写入、周度调度、回执及快照；源中断自动告警。

责任分工（待确认）

产品设计牵头，研发、测试、数据及对应业务协作；人员与投入待确认

可行性与投入

技术复杂度较低，主要难点是状态语义与关联关系。节省的周报工时可能不足以支撑独立专项，需同时测漏办减少与管理质量；价值不够则作为共享小自动化先落地。 优先复用现有工具，无需预设采购；增量资金待核定调用量后确认。低频项目四周运行仅约4个周度任务，不能把子项数当成独立周报任务扩充样本。

资源就绪后的四周MVP建议

用于建设与小范围验证；不能代替后续持续真实运行验收。低频任务样本不足时延长观察。

冻结需求池范围、状态权威顺序、停滞规则和历史对照，测人工成本。
自动拉快照与生成事实周报，逐项核对遗漏与来源。
接通冲突核实任务和回执，演练断连与跨周续跟踪。
观察接收方能否直接使用；低频样本不足延长观察，不提前宣告达标。

停止 / 收窄 / 降级条件

若关联关系长期不可靠或正常周报仍需大段人工改写，维持L2；若净节省很小且质量无改善，不占专项名额。

一个任务如何完成

设计示例，非已发生业务

某需求上周写“测试中”，本周Jira无更新而聊天说“快好了”：系统保留测试中，列入待确认，并给owner带来源的核实任务，不自动写为已完成。

验收口径与准入闸门

真实计量单位

一个团队一周的治理周期，覆盖冻结范围内全部未结束需求；按期输出、冲突有责任人与回执才完成。任务卡数和周报数分开统计。

专项指标

来源覆盖；无依据进展；停滞漏检；每周净节省

当前不可声明已达标。负责人、真实SOP、基线、权限与持续运行证据仍待补齐。

自动交付比例＝无人工介入且达到冻结交付标准的有效任务数 ÷ 全部准入有效任务数。失败、转人工和超时不得从分母删掉；必经逐单审批计为人工介入。客户自主确认是必要步骤，应如实计量，不以“异常”名义排除。

净人工时包括资料整理、规则维护、复核、异常、返工与运维；构建投入单列。独立盲测与同口径人工基线比较，不只让生成模型自评。建议目标先审批冻结，实绩未知时显示待测。
