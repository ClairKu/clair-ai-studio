01一句话结论

盈米正在形成的不是四个分散的 AI 产品，而是一条完整的金融服务生产链：

数据与知识 → OAP 能力层（MCP / Skills / Agent）→ AI 实验室编排层 → AI 小顾与顾问工作台交付层 → 用户反馈、合规与能力治理。

当前最大的机会不是继续堆工具数量，而是把这条链真正接通：统一身份权限、统一能力目录和质量门槛、统一指标口径、统一任务结果回流。否则能力越多，治理、发现、复用和商业化的摩擦越大。

关键判断：

  1. OAP 是能力操作系统，不应只按“多少个工具、多少次调用”衡量。 应转向成功任务、有效用户、复用、质量和收入。
  2. AI 实验室不是新的工具列表，而是服务生产与发行机制。 它的价值来自“能否将已有能力快速组装成可运营服务”。
  3. AI 小顾 3.0 与顾问工作台共享同一套底层能力和服务对象。 两端应该共享客户授权、任务、记忆、报告和服务结果，而不是各自再造。
  4. 报告 Skill 是最接近业务闭环的切口。 它具备明确输入、确定性计算、可审查输出和可量化效率，适合成为能力治理样板。

  • 公司逐步积累大模型应用、投研数据、投顾工具和内容生成实践。

  • 2025-03 启动 AI 开放平台。
  • 2025-04 官网与开放申请上线。
  • 2025-05 发布首批 MCP 能力。
  • 后续出现 C 端平台接入、首笔收入、阿里云合作、金融大模型/评测集、用户与调用破阶段里程碑。
  • “全民 AI / AI 实验室”构想形成：员工与用户可以生产、发布、订阅和分享金融服务。

2026：从 MCP 工具走向 Skills、Agent 与连续服务

  • 2026-04 发布首个投顾 OpenClaw 服务。
  • 2026-06 发布首批 Skills。
  • 能力接入 AI 小顾，AI 小顾 3.0 转向记忆、主动监控、深度分析与连续服务。
  • 顾问报告 Skill、工作台、多 Agent 架构和服务生产平台同步推进。

054. OAP：从能力开放到能力经营

已经形成的基础

  • 能力形态覆盖 MCP、Skills、Agent。
  • 已进入外部流量平台和云/Agent 平台合作场景。
  • 有 C 端用户、金融机构、非金融机构、调用量和商业意向的多组阶段性证据。
  • 已出现首笔收入、招投标、额度采购意愿与平台合作。

材料明确暴露的问题

  • Stargate、Agent/Skills 管理平台等多个中后台未完全打通。
  • MCP 的正式能力、底层路由、能力分组、分类与质量口径混杂。
  • 2026-07-21 路线图材料显示：69 个正式能力、1,849 条底层路由、34 个能力组；大量路由未分组、未分类。该数据是特定日期快照，不等同于当前实时状态。
  • 供给侧仍偏“数量证明”，有效场景、成功任务、可复用服务、质量和计费证据不足。

应从“工具运营”升级为“能力经营”

建议把供给漏斗改为：

候选能力 → 质量评审 → 正式能力 → 场景组合 → 成功任务 → 可复用服务 → 付费/SLA。

建议新增六类运营对象：

  1. 能力：MCP / Tool / API
  2. Skill：带脚本、参考、资产和输出契约的任务能力
  3. Agent / Workflow：有状态的编排
  4. 服务：可被用户理解和订阅的场景产品
  5. 结果：报告、诊断、提醒、交易前建议等可复用产物
  6. 反馈：人工修改、采纳、失败原因、后续动作

065. AI 实验室：金融服务的生产与发行层

材料中的核心构想是“人人可创作、使用、发布和分享”，但其真正壁垒不是低代码界面，而是盈米能把以下内容放入同一服务：

  • 用户自己的数据和授权；
  • 平台数据、投顾工具和金融计算；
  • MCP / Skills / Agent；
  • 投研知识与检索；
  • 文本、图表、报告、组件等多种结果形态；
  • 发布、订阅、市场与反馈。

三张画板呈现了同一方向：

  1. 关系图：AI 实验室负责生产与发布服务，AI 小顾负责消费服务，并将偏好和结果反馈回去。
  2. 分层图：应用层下面是 Agent/Workflow、Skills、MCP/Tool，再下面是用户、资产、金融数据和 RAG。
  3. 产品地图：服务由模型、Agent、工作流、插件、知识库和用户偏好共同组成，可输出文本、图表、报告或交互组件。

需要补齐的不是更多组件，而是：

  • 服务模板与适用人群；
  • 数据授权范围；
  • 上线前测试和人工审核；
  • 版本、下线和依赖管理；
  • 发布后的触达、订阅和效果反馈；
  • 计量、计费和收益分配。

076. AI 小顾 3.0：从回答问题到持续服务

两份产品材料将 3.0 定义为四个能力：

  1. 更懂你：建立长期记忆和偏好。
  2. 更主动：通过“小顾帮你看”等周期任务持续监控。
  3. 更会分析：结合个人数据、市场与投资组合做多维分析。
  4. 更有结果：输出提醒、诊断、报告和后续动作，而不是只给一段文字。

可抽象为连续服务循环：

建立授权和记忆 → 配置任务 → 自动监控 → 生成分析 → 人/用户确认 → 采取行动 → 结果反馈 → 更新记忆。

这意味着产品指标也必须变化：

  • 不只看对话数，应看任务开启率、任务持续率、建议采纳和问题解决。
  • 不只看周活，应区分问答用户、任务用户、订阅用户、发生服务结果的用户。
  • “转化”必须注明是交易转化、运营触达转化，还是报告后服务转化。

087. AI 顾问工具：报告 Skill 是可复制的落地样板

报告生成方案

材料提出清晰的三层分离：

报告 = 数据 + 文案 + 呈现

  • 数据与计算：MCP Tool 或 Skill scripts，结果可复算、可验证。
  • 文案：LLM 只填写叙述性占位，不负责算数。
  • 呈现：确定性 HTML/PDF/PPT 模板和设计令牌，锁定结构、图表和品牌。

这一边界非常重要：LLM 不能改变列数、公式、图表颜色、布局和合规固定内容。

报告类型

  • 财务规划报告
  • 投资规划报告
  • 持仓检视报告
  • 策略运行报告
  • 产品方案报告

典型流程

  1. 从且慢/SCRM 获取授权数据，或由顾问上传外部材料。
  2. 脚本做家庭结构、收支、资产负债、财务指标、现金流等确定性分析。
  3. 人工确认事实和关键假设。
  4. 调用投研观点、市场数据、策略/产品信息。
  5. LLM 生成受约束叙述。
  6. 模板生成 HTML/PDF/PPT。
  7. 顾问微调、版本管理、下载、分享和跟踪。

项目成熟度

  • 财务分析、投资规划、固定/半固定内容已有 Skill 方向和原型。
  • 市场观点、资产配置建议、宽基/固收/私募/债券/大类资产等投研数据仍有明显缺口。
  • 私募详情、净值、指数、目标测算、方案匹配等部分 MCP 尚缺。
  • 报告工作台与“顾问全生命周期 OS”之间仍需明确第一阶段边界。

从三份真实样例看到的共性

样例包含真实个人信息，本文不复述任何客户、顾问或资产明细。仅保留结构结论：

  • 50–80 页级报告有大量固定前言、公司/顾问资质、方法、投教和免责声明。
  • 核心可变部分集中在家庭画像、资产负债、现金流、风险、目标、配置、产品和执行计划。
  • 报告常见问题不是“不会写”，而是事实搬运、口径一致、公式准确、内容更新和版式统一。
  • 适合拆成独立模块，并在最终交付前设置事实与建议两个确认门。

098. 顾问工作台：应先做任务闭环，再做大而全 OS

建设方案将顾问工作台定义为 AI-native 的客户生命周期操作系统：

  • 前台：客户、任务、报告、服务计划、沟通和建议；
  • Copilot：理解当前客户和顾问上下文；
  • 多 Agent 后台：客户分析、投研、报告、合规、运营等；
  • 记忆：客户长期记忆与顾问工作记忆；
  • 服务引擎：将生命周期阶段转成下一步任务。

这个方向成立，但最容易陷入“架构正确、落地过宽”。建议顺序：

  1. 报告任务：数据 → 人工确认 → 计算 → 文案 → 交付 → 后续任务。
  2. 监控任务：配置 → 触发 → 分析 → 提醒 → 处理结果。
  3. 服务计划：按客户阶段组织报告、监控和沟通任务。
  4. 再扩展为完整生命周期 OS。

109. 指标口径冲突：目前不能合并成单一“最新值”

同一业务在不同日期、用途和材料里出现不同口径。以下数字应保留来源与日期，不应挑一个作为“当前事实”。

指标材料中出现的值可能差异来源结论
能力/工具数69 个正式能力、72 个工具、近 80 个 MCP 工具；另有 1,849 条底层路由正式能力、展示工具、MCP、底层接口不是同一对象必须先建立能力对象字典
用户/申请用户7,000+、7,443、7,500+、8,289日期、申请/注册/使用、站点/平台口径不同不可直接比较增长
累计调用8.2M+、8.8M、9M+、9.029M、9.145M日期、MCP/服务/全站口径不同需要同一数据源和截止日
机构369+、400+ 金融机构、1,450+ 全部机构金融机构、申请机构、所有机构不同应拆金融/非金融/合作/付费
AI 小顾用户18 万+ 等历史宣传快照产品阶段和统计窗口未标清不能当作 2026-07 当前值

建议发布统一指标字典，每个指标必须有：

名称、对象、分母、事件定义、去重规则、数据源、刷新频率、截止时间、负责人。

1110. 2026 下半年计划的可执行化建议

原计划围绕增长、供给和商业化，提出申请用户、调用、Skills、MAU、能力数量、平台合作和定价等目标。建议重构成一个北极星与四个护栏。

北极星

月度成功金融服务任务数 一次任务必须满足：有明确场景、调用成功、输出通过质量门槛、被用户/顾问消费，并记录结果。

四个护栏

  1. 质量：成功率、人工退回率、合规问题率、P95 时延。
  2. 用户价值：任务完成率、复用率、建议采纳率、30 日持续率。
  3. 供给：正式能力覆盖、优质 Skill/服务数、依赖健康度。
  4. 商业：付费机构、付费能力、收入、单任务成本与毛利。

优先级

P0：统一能力和指标底座

  • 统一能力目录、版本、权限、依赖、质量状态和 owner。
  • 区分正式能力、底层路由、Skill、Agent、服务。
  • 统一埋点和指标口径。

P1：打穿 3 个种子闭环

  • 顾问报告
  • AI 小顾周期监控
  • 机构嵌入式金融 Agent/服务

P2：建设 AI 实验室的生产发行机制

  • 从模板创建、测试、审核、发布、订阅、运营到下线。

P3：验证商业化

  • 免费额度、按量计费、套餐/SLA、项目制交付分别验证。

1211. 主要风险与控制条件

风险证据控制条件
客户隐私泄漏样例报告含真实 PII、资产和持仓默认脱敏；最小授权；生产数据与 Demo 隔离；分享前自动扫描
LLM 产生计算错误报告涉及大量指标和测算计算必须由脚本/工具完成；记录输入、版本和公式
观点过期或来源不明市场观点模块仍在确定维护方式每条观点带来源、作者、适用期和截止日；过期自动阻断
能力数量虚高正式能力与底层路由混用目录按对象分层；正式能力需要质量门槛
规划被误读为已上线多份材料同时包含已完成、目标和方案状态统一为：已上线/试点/开发中/规划/待决策
