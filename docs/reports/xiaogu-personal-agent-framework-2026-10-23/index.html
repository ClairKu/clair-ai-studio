01

产品定位：用连续服务促成转化

AI 小顾承载主要服务；APP、千问与真人服务成为同一套能力的不同接触面。

让每个用户在每次接触时，都能从当前需求出发，得到适合自己的下一步，并接着上一次的进度继续完成。

业务目标

提升新客有效首投转化与老客持续经营效果；通过解决具体阻碍、降低理解和操作成本形成增量。

核心执行对象

用户 × 独立需求 × 服务阶段。一个用户可以同时有攒钱、理解回撤、开户等多个需求，每个需求都有进度和结果。

平台共同底座

每个用户拥有持续更新的运营服务包。系统、AI、顾问、运营、私域和客服按职责读取与推进同一服务状态。

产品边界要先说清：“知道所有用户信息”落实为在授权范围内整合服务所需信息，同时明确未知、过期和推断。转化是业务目标，用户的资金用途、适当性与自主决定构成服务前提。
形态决定什么典型结果
传统产品：千人一面产品预设页面与固定操作顺序每个用户寻找同一套功能
智能运营：千人百面规则选人群、选内容、选触达时间不同客群收到不同内容
Personal Agent：千人千时千面基于用户目标与实时状态决定做什么、怎么做、何时继续同一个问题也可以得到不同服务路径；跨入口连续完成

真正的个性化发生在服务动作、步骤、时机和责任交接上；语气和推荐内容的变化只是其中一部分。

用户侧：小顾是主服务面

入口展示“当前值得处理的一件事”；回答解决当前问题，并在有帮助时给出下一步；“我的服务”展示方案、进度、待办与历史。

业务侧：服务运营台

市场、运营与专业团队维护需求地图和资产；运营查看机会、异常与履约队列；顾问直接接管服务单，完成后可交回 AI。

03

用户运营服务包：一份可执行的服务档案

它同时记录“我们知道什么”“用户正在做什么”“接下来允许做什么”。

组成最小内容更新责任
身份与使用许可访客 / 账户身份、来源关系、授权用途、允许渠道、静默与退订身份和授权服务权威维护；变化立即生效
已确认事实与约束账户、持仓、风险测评、资金用途与期限；每项标明来源和时点业务系统提供事实；关键决策实时核实
需求、偏好与记忆用户目标、沟通偏好、历史原话、确认结果；AI 推断单列每日整理；重要事实确认后即时写入
行为、路径与来源首触与本次来源、活动 / 内容承诺、前序页面、点击与失败事件、跨端续接点事件即时更新；区分事件发生时间与到达时间
服务单、承诺与待办需求、阶段、阻碍、已交付、等待事项、责任人、恢复条件每次动作回写；可跨会话、跨渠道恢复
候选计划与效果候选下一步、理由、前置条件、已有服务与转化证据候选随状态失效；只有执行回执才能推进阶段

三个层次，避免混成一段摘要

事实层：权威数据和用户确认的信息。
判断层：AI 对需求和阻碍的候选解释，附证据与有效期。
行动层：当前服务单、下一步、执行权限与结果。

同源读取，按角色裁剪

AI 只取当前服务需要的上下文；顾问看目标、事实、障碍与承诺；运营看阶段与履约；系统读取结构字段和执行条件。共用状态不等于每个角色都看全量信息。

服务包示意 · 虚构用户 · 无真实账户连接
服务包的数据契约：给产品和研发的最小约定

外层记录 user_ref、身份级别、包版本、快照时点、事件水位、授权版本与完整度。重要字段记录 value、source_ref、observed_at、effective_at、expires_at、verification_status。推断额外记录证据、待确认问题和失效条件，不把模型自评分当事实可信度。

服务单记录 service_id、need_id、stage、status、blocking_reason、owner、next_step、receipt_ref 与 version；调用时携带 actor、purpose、surface、capability_scope 与 package_version。接口输出数据、来源、缺失项和允许动作，避免调用方自行猜测。

建议最小能力：读取服务上下文、追加事件、查询候选动作、执行授权动作、校验执行回执、推进服务单、交接真人、撤销许可。写操作需校验版本并防重复；权限由服务端校验。

04

日增量与实时服务：两种速度，一份状态

日更新负责长期理解，实时更新负责眼前判断；持仓与资金事实保留各自的业务时点。

每日：整理底稿

归并新增对话与服务结果，更新目标进展和未完成事项，校正过期记忆；仅重算变化部分。

实时：叠加变化

当前提问、浏览、操作失败、交易结果、授权变化和人工记录，更新当前服务状态。

调用时：核实事实

需要用到余额、测评或交易结果时，读取权威接口。市场行情、持仓估值与成交状态分别标注更新时间。

执行后：写回闭环

保存交付物、真实回执、阶段结果和下一步；下一次服务直接恢复。

防止“旧画像指挥新动作”：关键字段过期则刷新；刷新失败就明确未知，选择补问、降级或暂缓。交易结果不确定时先查询状态。重复事件防重，迟到事件按版本与发生时点归并；业务事实与用户自述冲突时并列保留并澄清。
对象建议首期更新方式验收重点
授权与退订撤销后立即阻断后续调用与触达缓存、记忆、计划和渠道同步失效
行为与对话会话内更新；关键事件秒到分钟级目标待压测不遗漏关键失败事件；无事件不等于无需求
持仓、资金、订单沿用权威业务时效；关键动作前复查可查时点与口径，不能承诺所有数据逐秒准确
长期理解与服务摘要按日增量；关键确认即时写入可重建、可修正、可按需删除或停止使用

覆盖全体用户，同时控制成本：每天核对所有服务包的变更与未完成事项；无变化时保留有效版本，有变化时只重算受影响部分。重要事实实时刷新；按需加载原始记录。冷用户无需每天重复调用模型生成同一段总结，模型预算优先用于需求发现、矛盾识别和正在推进的服务。

以上为设计目标，接口可用性、更新延迟和容量待联调；不要先启动“全量数据搬家”，应由首批服务闭环反推必需数据。

05

触发：从规则命中，走向有证据的服务机会

规则保证确定性，模型发现变化与矛盾，系统判断此刻是否值得行动。

触发来源模型 / 系统需要识别什么合理下一步
用户主动请求明确需求及缺失前提立即服务，必要时只补问关键问题
实时行为与操作停在哪一步、是否有错误、是否刚完成修复操作阻碍或恢复任务；避免把浏览当购买意愿
每日跨天扫描承诺到期、目标变化、需求反复未解决恢复已约定服务，或提出有依据的候选
市场与持仓变化该变化对这个人的目标和资金是否有实际影响解释、核实需求、复核方案；不默认推交易
对话、记忆与事实矛盾用户说近期用钱，现有计划却长期锁定先澄清资金约束，必要时调整服务方向
人工及跨端交接前一个服务者留下了什么承诺和待办接着做，避免重复询问或重复触达

机会卡应给出可审查的理由

出现什么证据 → 可能是什么需求 → 对用户有什么价值 → 缺什么信息 → 候选服务 → 允许的渠道与时机 → 何时失效。模型发现新问题时可以提出新需求类型，由运营评估是否沉淀。

全局仲裁决定要不要打扰

先处理用户当前请求、服务失败和到期承诺，再考虑经营机会。统一考虑用户价值、需求把握度、紧迫性、打扰成本与执行成本；等待、不行动、转真人都是合法结果。

首期用可解释的优先级与约束，积累真实结果后再学习排序；模型评分不直接代表购买概率，也不直接拥有触达权限。

06

入参：每一次服务，组装一份当下上下文

保留稳定底稿，按需读取实时信息与原始证据，避免一次把所有历史塞给模型。

用户是谁

身份可信程度、账户状态、已授权数据与可用渠道。

想完成什么

当前独立需求、资金用途、期限、约束与成功标准。

刚经历什么

本次来源承诺、对话、路径、失败事件和当前页面。

以前做过什么

已交付内容、已有方案、拒绝原因、人工承诺与待办。

现在有什么变化

持仓与市场变化、资金到账、目标变化和新事实。

能做什么

当前可用工具和服务资产、适当性前提、渠道能力与动作权限。

例：“新客 + 看过三次产品页”只能提示可能需要帮助；“用户说担心三个月后用钱 + 刚查看赎回规则”能支持先解释流动性并确认期限。相同标签的两个人，服务方向可以完全不同。

来源链单独保存渠道、内容 / 活动、来源任务、会话与事件关联，保留首触、本次触达和辅助触点。来源关系用于接续和解释，不直接等同因果归因。
上下文优先级建议：当前明确请求 → 当前服务单 → 决定性事实 → 相关已确认记忆 → 相关历史与证据 → 模型候选判断。用户当前纠正的信息应更新已过时记忆，并触发依赖它的方案重新核验。

一张资产卡的最小字段

资产 ID、解决的问题、适用 / 禁用条件、必需入参、可用渠道、输出格式、成功证据、失败处理、责任人、审核状态、版本、有效期与成本。

把边界审核前移到资产发布

专业团队审核方法和事实，市场审核表达与承诺，运营审核适用条件和节奏。发布后，AI 在已批准边界内选择和组合；超出边界时补问、降级或交接。

资产样例：首次投入前的流动性疑问

服务目标：帮助用户理解资金可用性并确认自己的期限。
入参：用户资金用途、预期用钱时点、所讨论方案、有效规则来源。
执行：信息不足先问期限 → 调取对应到账与风险说明 → 比较适用资金安排 → 让用户选择继续或暂缓。
完成证据：解释卡片已呈现；期限已确认且该阶段问题已解决；服务状态与下一步已写回。用户主动结束另记取消，除非已有目标完成证据。
禁用：承诺随时无损取出、把未确认资金认定可投资、没有有效来源却输出到账期限。
责任：运营维护问题地图，专业团队维护规则，产品研发维护查询与展示。

08

AI 如何编排：每一步都能核验和接续

模型负责理解与选路；系统负责身份、权限、约束和执行状态。

1 / 识别与核实

读取服务包与当前请求；核实决定性事实；信息不足时选择必要补问。

2 / 规划与校验

生成候选路径；检查适用性、权限、资产有效性和触达冲突；选择当前一步。

3 / 执行与交付

调用工具与资产；输出解释、方案、引导或人工交接；等待用户决策时暂停。

4 / 验证与更新

核验回执和业务结果，推进服务单；失败则恢复、降级或交接；写明下一步。

识别需求→待补信息→可服务→执行中→待用户 / 待外部→已核验完成

任一阶段都可进入失败待恢复、真人接管、用户取消或不适用；“等待”属于可恢复状态，不自动记为完成。

动作类型AI 的权限建议执行边界
查询、解释、测算、服务单维护可在授权范围内自主完成来源有效、方法可用、记录调用与结果
提醒、站内引导、流转任务满足既有许可和约束后执行统一频控、有效期、送达回执、重复动作防重
身份关联、重要信息确认、交易等用户决定请求用户明确确认复用合法有效的既有授权；关键业务动作走正式流程
重大事实冲突、复杂个案、投诉、能力外问题自动交接到明确责任队列包含目标、证据、已做事项、阻碍、下一步与接单回执
服务完成的四个凭据：有可核验结果或交付物、有真实呈现 / 送达凭据、有状态写回并读取确认、有明确结束或下一步。四项只是必要凭据，各类服务还要预先规定目标完成标准。生成成功、工具已调用、发起了跳转都不足以单独证明服务完成；已完成解释也不代表已完成首投。

真人接力状态：待接单 → 真人已接管 → 待交回 → AI 已恢复。接单前原责任方继续承担承诺与用户咨询；接单超时进入备用队列或恢复可提供的 AI 服务，并向用户说明。交接与交回均核验版本，原触达计划随接管状态暂停或取消。

方法参考：Anthropic 区分预定义流程与由模型动态决定步骤的 Agent，并强调清晰工具与反馈。本方案采用边界明确的动态编排，具体经营机制为本报告建议。阅读原文 ↗

场景：从千问新客开始，验证全生命周期复用

场景用“来源 × 账户状态 × 独立需求 × 阶段 × 当前阻碍”组合，减少僵硬客群剧本。

千问身份链：临时访客服务单 → 安全续接凭据 → 到达且慢 → 登录验证 → 绑定账户 → 区分真正新客、老户首次投资与老户回流。跨平台能传什么、能否稳定带回进度，必须联调验证；传不过来时采用平台允许的接续链接或最少补问。

本页场景是预设示意，用于讨论状态如何影响服务路径；未连接千问、账户、持仓或真实模型。

验收：证明增量转化，解释服务为何有效

服务质量负责解释机制，随机对照负责判断业务增量；两套指标各自保留完整分母。

主试点业务指标建议

D14 有效首投率的实验组与对照组差值

D14 内完成有效首投的入组单元 ÷ 全部符合条件且已完整经过 D14 观察的入组单元

层次指标与定义要点避免误读
业务结果百分点差值、相对提升、置信区间；首投金额和 D30 留存作后续观察开户、入金、申购确认分别定义；不把点击当成交
服务完成达到预定义阶段目标且具备四项凭据的任务 ÷ 全部预定义入组服务任务失败、超时、转人工保留在分母；AI 自行拆出的子步骤不新增分母；自动完成率另列是否无人介入
阶段推进需求续接、信息补齐、方案交付、下一步到达、开户、有效首投同一队列固定窗口；多次服务不重复算人数
质量与体验错误事实、越权、错绑、过期信息、重复触达、投诉和退订重大问题暂停相关能力；阈值在试验前冻结
效率与成本有效完成服务的总成本、人工耗时、响应耗时成本计入失败、重试、渠道和人工兜底
老客经营场景阶段推进、对照组净资金变化、D30 / D60 资产留存和复访行情涨跌造成的资产变化与净资金流分开

先确定能稳定识别的实验单元

首期主因果实验在登录验证后、账户阶段服务发生前按账户分流，D0 从入组起算；结论限定为可识别阶段后的增量。匿名阶段只有可靠标识才单独做访客实验，上游另报漏斗。

坚持最初分组分析

在服务发生前分流。没继续聊、超时、转人工都保留；日志缺失标“结果待核验”并报告覆盖率和敏感性分析，不能只统计可追踪成功者或把未知默认为零。

账户与访客实验保留各自原始分组，不在登录后悄然覆盖；用验证后的关联映射分析跨端旅程。存在跨组曝光时记录污染，按预定方法报告，不能为追求好结果事后删样本；无法稳定去重时不宣称整条千问获客链路的因果提升。新客与老客首次投资、老客回流分别成队列。

实验节奏：先采基线与做 A/A 对账，再按基线、最小有业务意义的提升和流量计算样本。对照组保留原服务，实验组启用编排；观察窗口、首投有效状态、撤单处理、红线和停止规则预先冻结。八周是推进建议，不保证统计结论能在八周内成熟。

首期怎么落地：两条链路，八周推进

主链路验证千问新客转化，第二条验证 AI 与真人能共用底座。

P0 主链路：千问资金安排新客

有明确攒钱 / 资金安排问题 → 需求续接 → 必要补问 → 有价值的服务交付 → 合适的开户或投资下一步 → 结果回写。优先解决“到了且慢又重新开始”的断点。

P0 复用链路：老客新增资金咨询

用户主动询问 → 读取已授权持仓与目标 → 补齐变化 → 交付资金安排服务 → 必要时顾问接管 → 小顾继续。先验证服务连续性。

周期重点可交付验收 / 依赖
第 1 周共识与核查两条试点路径、10 类真实阻碍、身份和事件盘点接口 / 负责人 / 流量 / 基线均标待确认
第 2 周最小用户服务包可读服务包、服务单、授权与事件契约事实 / 推断 / 缺失分开，AI 和真人读同一进度
第 3–4 周资产与执行闭环15–20 项首批资产、编排、工具回执、真人交接两条端到端链路；包含失败、超时、拒绝、过期案例
第 5 周影子运行与 A/A不额外触达地验证候选决策、身份与事件对账随机分组稳定、回执可核查、质量门槛达成
第 6–7 周小流量随机试验原服务对照、编排实验、异常运营与版本记录不任意调整策略；必需修复保留版本和影响记录
第 8 周起成熟队列复盘增量、质量、成本、缺口和放量建议D14 只看完整观察队列；样本不足则继续收集

P1：扩展到首投前阻碍处理、到账后续办和首次持有陪伴。P2：在闭环质量稳定后扩到持仓变化、APP 页面与行为点，逐步增加主动触达范围。

联合共创会：会后必须拿到可执行材料

建议一次 90 分钟工作会，完成范围、责任、接口与验收的第一版约定。

0–15 分钟

确认首期两条链路与转化定义，讲清业务目标和用户价值。

15–40 分钟

逐步走真实用户路径，找 10 类阻碍，标出已知、未知和系统断点。

40–65 分钟

选首批服务资产，确定维护、审核、工具与真人接管责任。

65–90 分钟

确认数据与身份依赖、实验口径、排期和每周验收。

会后六件交付物需求与阻碍地图服务包与事件字典首批资产清单两条链路验收用例分工与依赖表实验与停止规则
共创填写区

把待确认项变成明确责任

可填写并保存在当前浏览器，导出为 JSON。此公开讨论页仅填写职责与计划；真实用户资料留在业务系统。

最需要避免的六个偏差

将试点的可用闭环作为进度，而不是把数据量、入口数或模型调用数当成果。

先做全量画像，服务迟迟不闭环

以首批需求反推数据，先让一件事从开始走到结果，再扩充覆盖。

把日更新摘要当实时真相

调用前核实决定性事实；计划和缓存随关键变化失效。

只有素材链接，没有执行能力

内容能找到之外，还需知道何时用、怎么执行、如何确认完成。

模型猜测成为永久事实

推断保留依据和有效期；重要信息经确认后才作为决策前提。

各渠道各推各的，越智能越打扰

统一服务单、责任人与触达仲裁；任务完成即取消旧计划。

只看“用过 AI 的人更容易买”

用随机对照测增量；服务完成与有效交易分别核验。
