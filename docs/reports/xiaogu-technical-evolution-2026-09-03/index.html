01 · Executive verdict

先看结论：小顾经历了三次本质跃迁

这不是“换了几个模型”的故事，而是服务组织方式、能力供给方式和价值验收方式连续换轨。

A

从功能入口，变成服务入口

2021 年已经定义了完整的投前、投后、财富旅程和账户管理，但用户仍要理解页面和模块。小顾把服务藏在对话与主动触发之后，用户只需表达目标。

“先有投顾服务系统，后有大模型；AI 的作用不是发明服务，而是让服务更容易被发现、组合和持续交付。”
B

从剧本路由，变成动态编排

早期是“意图 → 剧本 / 场景 Bot”；随后变成“总指挥 → 专家 Agent → 工具 / 数据”，复杂问题不再要求事先穷举。

核心技术跃迁
C

从一个产品，变成能力平台

MCP、Skills、Agent、OAuth、审计与多端分发，让同一项基金、账户或规划能力可以在小顾、顾问工作台和外部 AI 入口复用。

组织与商业跃迁
护城河 01

真实账户上下文

持仓、收益、资金流、风险偏好与交易状态，让回答从“金融百科”变成“与我有关”。

护城河 02

投顾方法论

四笔钱、规划、诊断、陪伴与合规边界，构成可被模型调用的专业 SOP。

护城河 03

工具与口径

模型负责理解与解释，计算、查询和业务动作交给确定性服务。

护城河 04

服务闭环

结果、采纳、失败和反馈回流，才让一次问答变成可复用服务资产。

03 · The prehistory

0 阶段不是聊天机器人，而是投顾服务操作系统

2021 年的原型已经包含投前、投后、财富旅程和账户管理。这个骨架后来被 AI 重新编排，却没有被替代。

产品框架

“小顾模式 + 财富旅程”双轨

互动服务负责当下问题，静态旅程负责开户、签约、里程碑与月度报告。它本质上已经是一个事件驱动的投顾服务蓝图。

关键遗产

四笔钱不是 UI 分类，而是推理坐标系

活钱、稳钱、长钱、保障把用户目标、风险、流动性和产品匹配连接起来，后来成为模型解释、工具调用和卡片输出的共同语义。

早期局限

服务多，但入口仍靠人找

模块越多，导航和运营配置越重；用户不知道去哪、怎么问、下一步是什么。AI 小顾最初要解决的正是“发现服务”的成本。

04 · Architecture

今天的小顾，可以拆成十层

下面把产品、模型、数据、工具、治理和分发放到同一张图里。越靠左越稳定，越靠右越接近用户与经营结果。

L0

投顾方法

四笔钱、规划、诊断、陪伴、合规话术、人工接力。

最早形成，最不该被模型绑架
L1—L2

数据与知识

账户持仓、交易、基金与行情、投研内容、RAG、引用溯源。

决定“与我有关、言之有据”
L3—L4

Tool / MCP / Skill

查询、计算、图表、报告、业务 SOP 与质量门。

把模型判断落到确定性能力
L5—L6

Agent 编排

意图识别、问题拆分、总指挥、专家 Agent、工作流与人工确认。

从“匹配答案”升级为“完成任务”
L7—L9

交付与经营

卡片 / 报告 / 动作 / 持续任务；App、微信、千问、顾问工作台；审计与计量。

最终价值发生在这里

横向控制面：身份与授权、Scope、敏感字段、内容审查、版本、监控、成本、审计、SLA。没有这层，金融 Agent 只是一个好看的 Demo。

06 · Generation 1

第一代：剧本 + 31 个场景 Bot，先把“能用”做出来

2023 年方案把小顾定义为且慢超级入口：主动引导、意图识别、智能服务、智能回复与搜索。2023.12—2024.06 日志证明这套架构真实运行。

49,495日志事件2023-12-20—2024-06-13
10,461用户消息记录同一导出文件
31独立 Bot 标识收益、资产、基金、市场等
2,362明确路由事件TRANSFER_TO_BOT

典型链路

用户输入 / 快捷菜单 / 自动引导 → 意图识别 → 场景路由 → 专用 Bot → 真实数据接口 → 结构化回答或人工接力。

  • 高频 Bot：搜索、收益分析、组合策略、账户报告、资产分析、资金流。
  • 查询模式已包含 SELF_INPUT、QUICK_MENU、AUTO_LEAD、OPTION。
  • 价值：先用确定场景获得稳定性，再逐步放开模型自由度。
07 · Generation 2

第二代：LangChain + 多模型 + 专家 Agent，扩展问题广度

单个 Bot 擅长一个问题，但复杂任务会跨越市场、产品、账户、风险和规划。Agent 化的核心是允许系统动态拆解并调度专家。

Before

静态分流

提前列出意图和剧本，命中后转专用 Bot。稳定、可控，但新问题需要继续加分支。

  • 优点：边界清晰、容易兜底
  • 缺点：长尾问题进入“其他”
  • 维护：场景越多，路由和回归越重
→
After

总指挥 + 专家

模型理解目标、拆步骤、选择工具与专家，必要时并行处理，再综合成答案或任务结果。

  • 优点：复杂问题可组合、能力可复用
  • 缺点：链路更长、成本和错误面增加
  • 治理：必须记录计划、调用和证据
为什么要多模型

速度、专业度、推理深度三角

通用 Qwen 负责常用投资咨询，DeepSeek-V3 作为同类通用模型，R1 面向复杂深度问题。模型切换不是“谁更聪明”，而是质量、时延、成本与可用性的路由。

当时产品说明明确提示：深度模型虽然思考更长，但可能无法稳定获取投资信息。深度推理不能替代工具可用性。
08 · Knowledge + tools

RAG 解决“凭什么这么说”，工具解决“数字到底是多少”

这是金融 AI 最重要的分工：语言模型负责理解与表达，知识库提供可追溯上下文，确定性工具负责查询、计算和动作。

01

内容 RAG

原始内容切片 → 语义检索 → 相关段落 → 大模型总结 → 逐句引用与原文跳转。

降低幻觉
02

账户工具

收益、回撤、四笔钱、风险测评、资金流、订单与持仓。

提供个性化事实
03

研究工具

基金详情、诊断、相关性、回测、蒙特卡洛、市场温度与指数估值。

把判断落到数据
04

结果工具

图表、HTML、PDF、报告模板与行动卡片。

把答案变成交付物
关键边界：RAG 只能提高“有出处”的概率，不能证明出处本身是最新、适用或数值一致；工具只能提高确定性，不能自动解决字段口径、上游错误和权限缺失。
09 · Generation 3

第三代：MCP / Stargate，把小顾能力从“内部接线”变成“可治理资产”

2025.04 起，能力不再只服务小顾。数据、算法、工具和内容通过开放平台注册、分组、授权、审计和分发。

协议层

MCP + OpenAPI

客户端通过 SSE / Streamable HTTP 获取工具 Schema 并调用；Stargate 动态生成工具清单、转发上游并记录成功调用。

网关层

代理 + 局部改写

大部分出参由上游决定，少数路由用 wrapper 脚本裁剪、转换或注入文案；还包含限流、额度、编码和错误处理。

渠道层

同能力，不同可见集

2026-08-31 快照：小顾 3.0 通用渠道 89 工具、卡片渠道 15 工具。69 是阿里百炼渠道资产数，不是全平台总数。

10 · Key changes

十个关键变化：每一次升级都改变了“谁承担复杂度”

好的 AI 产品不是不断把复杂度推给模型，而是把复杂度搬到最适合承担它的层。

01

页面找功能 → 对话表达目标

复杂度从用户导航迁到意图理解与服务编排。

02

被动问答 → 主动引导

开场、资产摘要、待办、市场温度和在途资金成为服务触发点。

03

单轮 FAQ → 多轮任务

从解释概念，走向读取数据、拆解问题、调用工具、生成报告和追问修正。

04

场景 Bot → 总指挥 + 专家

从穷举意图变为动态规划，新增场景的成本从“重做链路”降为“复用能力”。

05

单模型 → 多模型路由

速度、成本、深度和可用性按任务权衡，而不是用一个模型包打天下。

06

模型记忆 → 业务可控记忆

记什么、保留多久、何时更新、能否撤回，必须成为产品与合规规则。

07

内部 API → MCP / Skills

数据与 SOP 被标准化为可鉴权、可测试、可复用、可计量的服务资产。

08

API Key → OAuth / Scope

从“谁拿到 Key 都一样”转向识别平台、客户端、用户和授权范围。

09

定时任务 → 事件 / 指标触发

市场、持仓、任务状态变化触发服务，更精准，也减少无效轮询与 Token 消耗。

10

对话量 → 成功服务任务

调用、曝光和消息数只是过程；结果采纳、任务完成、复用与合规才是价值。

11 · Value

价值不只在“回答得更快”，而在五个层级

历史材料里存在不同时间与口径的数字。这里保留证据边界，不把不同快照拼成虚假的连续增长。

90%+问题解决率正式汇报口径；定义需复核
60%人工干预下降正式汇报口径；基期未披露
14%+入金转化使用服务后的用户口径
10万+使用用户2025.05 版本材料

用户价值

降低获得专业服务的门槛

把功能、内容、数据和顾问方法组织成“下一步”，减少不知道问什么、去哪找、怎么判断的成本。

业务价值

连接服务与转化

从账户问题、产品判断和市场解释自然进入规划、投顾服务与行动，但必须以归因链而非相关性证明。

组织价值

让专家方法可复制

Prompt、规则、脚本、模板、质量门和数据接口可以沉淀成 Skill，而不只存在于个别同事脑中。

技术价值

一次建设，多端复用

同一能力可以服务小顾、顾问工作台、微信、千问与机构 Agent，减少重复开发和重复口径。

治理价值

可授权、可追溯、可复核

金融建议不仅要“像对的”，还要知道读取了什么、调用了什么、哪一版、谁确认过。

战略价值

从 C 端产品走向金融 AI 底座

小顾验证服务价值，OAP 把能力资产化，外部入口与机构场景再放大分发和商业机会。

数字边界：材料中同时出现 8万+ / 10万+ / 15万+ / 20万用户、80万+ / 100万+ / 180万+ / 300万问题或调用等表述。未统一分母、周期、去重规则前，不应做连续增长结论。
12 · Failure modes

十二个坑：真正难的不是模型，而是系统边界

每个坑都给出根因与更优解。这里既包含历史实证，也包含从生产架构直接推导出的高风险点。

把“小顾”等同聊天框

对话只是入口，真正价值在服务、工具、数据与动作。

根因：以 UI 定义产品解法：以成功服务任务定义产品

场景 Bot 越加越多

31 个 Bot 能覆盖高频需求，也会带来路由、提示词、回归和版本爆炸。

根因：用分支对抗长尾解法：黄金场景固定，长尾交给动态编排

“其他”掩盖分类失真

点赞分析把 45% 归为“其他”；其进一步拆分比例并无原始标注证据。

根因：分类体系与真实问题脱节解法：人工抽样重标 + 在线混淆矩阵

深度模型不等于可靠数据

R1 能思考更久，却可能拿不到稳定投资信息；没有工具链，推理越长越像幻觉。

根因：把知识与计算都压给模型解法：模型规划，工具取数，规则校验

RAG 有引用仍可能错

召回旧内容、切片断义或引用错配，仍会产生“有出处的错误”。

根因：把引用当真实性证明解法：时效、适用性、数字三道校验

Schema、Wiki、代码三套口径

收益、回撤、市场温度、热门基金等关键逻辑大量只在代码或网关脚本。

根因：文档不在发布链路解法：从生产快照自动生成口径手册

工具数量越报越大

29、41+、50+、69、89、15、数千注册路由对应不同渠道与定义。

根因：资产、工具、渠道、版本混算解法：统一 Tool ID + 渠道可见集 + 版本

网关 wrapper 成为口径黑洞

字段裁剪、日期转换、15 点过滤和文案注入藏在生产脚本里。

根因：适配逻辑脱离契约解法：声明式转换 + 版本化测试样例

授权成功 ≠ 服务可用

OAuth 回调、工具列表、后端批准、Scope、真实调用是五个不同状态。

根因：把连接过程当结果解法：最小只读任务端到端验收

多 Agent 带来成本与延迟

计划、并发、重试和综合会放大 Token、时延与失败面。

根因：每个问题都走重编排解法：路由分级 + 缓存 + 确定性短路

记忆会放大个性化，也会放大风险

错误、过期、敏感或越权记忆会长期影响建议。

根因：把上下文存储等同用户记忆解法：分层、可见、可改、可撤、可过期

漂亮报告不等于任务完成

图表和 PDF 可能正确渲染，却仍有数据口径、适用性与合规问题。

根因：把输出完成当业务完成解法：证据、复核、采纳和后续动作闭环
13 · Generation 3 → 4

3.0 / 4.0 的关键，不是再加 Agent，而是让服务持续运行

从一次对话跨到长期关系，需要状态、记忆、触发、动作、授权和回写六件事同时成立。

读

读取状态

持仓、目标、风险、计划、任务、历史结果与用户授权。

判

发现问题

不是每天轮询，而是条件、指标或事件达到阈值时触发。

做

编排服务

调用 Skill / MCP / Agent，生成解释、卡片、报告或待确认动作。

记

结果回写

记录用户采纳、修改、失败原因与偏好，形成下一次服务上下文。

14 · Better architecture

更优解：把小顾建设成“任务操作系统”，不是 Agent 大卖场

未来 90 天最值得做的不是扩模型或扩工具，而是把契约、状态与验收打牢。

1

建立统一 Financial Service Contract

每个服务明确：输入、授权字段、数据截止、工具版本、计算口径、输出组件、允许动作、失败兜底、人工确认、反馈回写。卡片、报告、Skill、Agent 都引用同一契约。

2

把任务状态机做成一等公民

统一 pending / running / waiting-user / waiting-human / failed / completed；支持幂等、重试、超时、补偿和断线续跑。SSE 只是展示层，不应承担状态真相。

3

从生产 Schema 自动生成口径与测试

发布时自动导出人可读接口手册、Golden Case 与变更日志；wrapper 改写必须声明并进入回归测试，彻底收口 Wiki / Schema / 代码漂移。

4

记忆与授权统一进 Policy Plane

把“可读取、可写入、可保留、可触发、可外发”变成可配置策略；用户能看、改、删，敏感信息默认短期，跨端共享必须重新确认。

5

建立黄金任务集与经营归因

优先验收持仓诊断、收益解释、资金计划、市场影响、家庭财务规划等任务；同时串起入口 → 授权 → 成功任务 → 采纳 → 动作 → 交易 / AUM / 留存。

6

VPC 采用控制面 / 数据面分离

共享规则、Skill、评测和版本治理留在控制面；客户数据、模型与执行留在私有数据面。通过能力清单和兼容矩阵降低每个 VPC 成为独立分叉的成本。
