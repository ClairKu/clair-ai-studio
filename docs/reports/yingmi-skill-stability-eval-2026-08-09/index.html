发现的三个问题，不混为一谈

稳定性、测试质量与静态资料漂移分别治理，避免把“判分失败”直接等同于“能力失败”。

P0 · Skill 路由

专用工具优先级不够硬

只问交易状态时，应显式规定优先使用 BatchGetFundTradeLimit；只有同时需要完整详情时才复用 BatchGetFundsDetail。

P0 · Eval 设计

词面断言过窄

“相关性”和“相关系数”语义等价。断言已改为接受二者，并完成 3 次复跑验证。

P1 · 工具目录

静态清单存在漂移

BatchGetFundsHolding 出现在 Skill 静态说明中，但本次实时 CLI Schema 不存在。边界处理稳定，目录本身需要同步。

建议的修复顺序

本轮只做测试与诊断，没有改动已安装的 yingmi-skill。

把交易状态路由写成可执行规则

新增一句硬约束：仅查询可申购/可认购/可赎回时，优先 schema + call BatchGetFundTradeLimit。

保留语义型 Eval，减少词面误报

核心字段与工具调用用脚本校验；自然语言标签接受等价表达，避免把文案差异当成能力波动。

让工具目录以实时 mcp list 为准

静态清单标注“可能随服务变化”，并对持仓类能力增加存在性检查和替代路径说明。

隔离评测运行环境

本机还有 15 个缺少 YAML frontmatter 的无关 Skill，以及多个无关 MCP 启动告警；没有影响本次结论，但显著增加噪声与时延。
