PROJECT 04 / 产品设计与质量

用户反馈归集分派与处置跟踪

将App反馈、获准读取的社区及业务群问题，统一转为有证据、责任人和状态的反馈事项。系统自动去重、分派、追踪超时与处理回执，帮助产品发现漏办和反复发生的问题。

团队与责任

背景与立项判断

反馈经常分散在用户留言、群消息与工单。若只做摘要，后续仍要人工查重、找人、追问，问题可能在“已回复”后继续存在。首期价值是把反馈流转与跟踪做完整，服务解决质量另行验证。

C · 拟建闭环与人工边界

首期作业边界

首期限定一个已有反馈入口与一个明确授权群，受理产品体验和规则查询类反馈；不全域抓取私人聊天。完成为反馈交给有效责任队列、回执已关联且到达可核验状态。用户问题是否解决必须有复现或服务证据；单纯建单只算受理完成。

01 / 拟建步骤授权入口新增事件触发
02 / 拟建步骤脱敏归类并识别紧急事项
03 / 拟建步骤语义加规则去重关联
04 / 拟建步骤补充公开复现信息与分派
05 / 拟建步骤接单回执和超时升级
06 / 拟建步骤关联处理证据并形成反馈台账
常规：证据齐全 → 按规则直接交付异常：缺证 / 冲突 / 超时 / 越权 → 保留状态、转责任队列

最终交给谁、完成是什么

产品与客服拿到问题描述、来源引用、发生版本、缺失信息、影响范围和工单状态。正常信息齐全事项自动分派并确认到达；缺信息、投诉、资金损失与隐私问题直接转人工，标明原因与紧急性。

规则与判断依据

紧急词与业务类别由业务确认，模型只作辅助分类；用版本、症状、功能与根因指纹去重。身份验证和客户专属账户解释转客服。可自动发送的仅限已批准的收讫或进度模板，首期默认内部交付，不主动对客回复。修复未复现通过不得标为问题已解决。

D · 所需资源、缺口与可行性

必须先补的依赖

授权入口、责任映射、状态写回、处理回执

基础设施支持

一个反馈增量接口、一个指定群的最小只读权限、Jira限定写入、owner映射、回执与定时检查、内网证据存储。客服敏感接口待需要明确后再申请。

责任分工（待确认）

产品设计牵头，研发、测试、数据及对应业务协作；人员与投入待确认

可行性与投入

受理和跟踪规则相对清楚，真实解决复杂问题的自动化准备度较低。先验证入口质量和责任映射，明确作业终点；若只能交一份摘要，仍是辅助能力。 预算待测。优先已有企业协作与工单能力；按每日有效反馈、消息归集量、模型调用、存储期限和人工兜底成本估算，不预设采购客服平台。

停止 / 收窄 / 降级条件

如无合法读取权限、owner不愿接单或无状态回写，不能立项为完整跟踪；收窄入口或维持L2。社区舆情与客户投诉处置不并入首期自动处理。

社区和App同时反馈同版本按钮失效：系统合并到一个根因工单，保留两份反馈链；开发说已修复后，复验仍失败则继续开放，避免把“研发已回复”写成用户问题已解决。

验收口径与准入闸门

真实计量单位

一条去重后的反馈事项，保留其来源消息数量与关联用户数。跨用户重复反馈不能简单删除，既要复用根因工单，也要保留每个用户的服务状态。

专项指标

漏分流；重复提单；超时；已回复未解决率

当前不可声明已达标。负责人、真实SOP、基线、权限与持续运行证据仍待补齐。

自动交付比例＝无人工介入且达到冻结交付标准的有效任务数 ÷ 全部准入有效任务数。失败、转人工和超时不得从分母删掉；必经逐单审批计为人工介入。客户自主确认是必要步骤，应如实计量，不以“异常”名义排除。

净人工时包括资料整理、规则维护、复核、异常、返工与运维；构建投入单列。独立盲测与同口径人工基线比较，不只让生成模型自评。建议目标先审批冻结，实绩未知时显示待测。
