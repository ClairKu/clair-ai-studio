02 / DESIGN LOGIC

最有价值的预测，是补上目标与成果之间的缺口。

“用户想完成什么 → 现在还缺什么 → 哪一步值得继续 → 用用户口吻写好。”

设计解释 这是对已见行为的解释框架，未被证明是 OpenAI 内部的排序公式。截图文案所强调的“线上生效、当前发布、别只看旧版”，体现出一种可取的方向：建议应保留关键验收约束，而不只是围绕最后一个话题生成常见问题。由于没有原对话，不能反推这条建议究竟依据了哪一轮、是否正确。

01放在下一步发生处读完结果后直接看到可发送草稿，减少转述推荐卡片的步骤。
02用用户口吻“继续核验……”而非“你可以问我……”，缩短从想法到表达的距离。
03单条弱提示灰字可忽略，选择负担较小；也因此会有默认效应。
04接受与发送分开先变草稿，再正常发送，保留修改、放弃与审视的机会。
05允许不出现任务完整结束、依据不足、方向需选择时，空结果也有价值。

容易被低估的收益

不擅长写 Prompt 的用户也能表达具体下一步；长任务中可以提醒核验、交付或收敛；产品能把能力转化成“眼下能做的事”。

容易被高估的收益

高接受率可能来自“省事”和默认偏向。若建议把用户带离原目标、重复制造工作，聊天更长反而是成本。已有错误也可能被下一条草稿继续放大。

层次静态核验结果它解释了什么 / 尚不能证明什么

模型与推理 L2读取源线程模型、provider、模式；effort 可被远端配置覆盖，在预测元数据中记录源线程模型。没有证据证明它一定由某个“更便宜的小模型”生成，也不能把输入框显示的主模型直接当作已确认的预测服务路由。
输出协议 L3结果为 {suggestion: string | null}，字符串会 trim；客户端追加 JSON schema 格式要求。存在“建议为空”的协议能力。未见固定字数上限、候选列表、置信度分数或多候选排名字段。
两种时机 L4live 在回答完成后后台请求；catch_up 在恢复／重进已完成线程时补请求。不是只能紧跟最后一秒显示。生成和当前输入框是否展示是两个不同阶段。
失效与缓存 L4主进程结果按 host/thread/latestTurn 缓存；新轮次开始清旧预测，线程最新轮次变化会移除旧项；该预测查询设置 retry:false。解决多窗口／返回线程的重复生成与旧建议残留。无限 staleTime 不代表跨新轮次永久有效。
门控 L2/L4可因模型、provider、plan mode、能力开关不合格而放弃；目标状态要求 ready、连接正常、已恢复、最后一轮不在运行、无 active goal 等。没出现建议不一定是“模型想不出”。不能据静态分支推断当前远端开关取值。
灰字层 L5ProseMirror 的 decoration／widget；select-none、inert、aria-hidden。正文须为单个空段落，非 IME 组合输入，且不与其他补全菜单冲突。未接受前真实编辑文档仍为空，避免误保存、误发送和输入法冲突。灰字并不是已经替用户写入的消息。
接受操作 L5本机包中无修饰键的 Tab／右箭头／Enter 都可把预测写入草稿，光标移到末尾；该处理器不调用发送。官方只介绍 Tab。额外按键是本机版本证据，不能推广为所有客户端承诺；“Enter不直接发送”不等于“Enter无响应”。
安全与观测 L6源轮次 moderation metadata 可抑制预测；埋点区分 generated、abstained、shown、accepted、submitted、edited，并记录 Prompt 版本与耗时等。能观察从展示到实际发出的漏斗；不能据此声称每条建议都经过独立完整审核，或已经证明了留存收益。

官方 App Server 文档另有临时线程 fork、轮次边界和中断机制，可作为底层概念的交叉参考；本次公开正文未找到面向开发者的预测专用接口。[O3]

判断是否存在一个自然、明确、有价值且有依据的下一步。
若目标已完成、上下文不足、方向需用户选择，或必须新增授权，输出空建议。
否则用用户口吻写一条简洁、可直接发送的指令，延续原目标和原有约束。

不重复刚完成、已拒绝或已关闭的事项；不把无根据的怀疑写成事实。
不诱导交易、支付、删除、发布等高影响操作，不将接受草稿等同执行授权。
沿用对话语言，不使用“你可以问我”等助手口吻。

输入建议：原目标与约束、最近用户消息、最终回答、已完成／未完成／证据不足状态、事实 ID、近期已拒绝建议。不要默认加入其他聊天、后台屏幕或未授权数据。

05 / TRY THE INTERACTION

亲手验证：灰字、草稿和发送是三个状态。

本地交互演示 预设样例，无模型调用、无数据上传。演示借鉴已核实的交互，并增加显式采用、关闭、过期结果验证等方案项。点击输入框后可试 Tab／右箭头／Enter 接受，第一次只变成草稿。

示意回答 · 非真实对话

直接输入会使预测失效；中文输入法期间不接受；Escape 关闭本轮建议。按钮与键盘都不会向真实助手发送消息。

“检验晚到结果”会发起一条模拟延迟请求，并在请求期间插入一段示意用户草稿。旧结果返回后须被丢弃。这里的 900ms 仅用于观察演示，不是原厂参数或性能。

验证状态：14项模拟 DOM／时钟行为测试通过，附件和包内镜像一致。独立浏览器预览连接不可用，本次未完成真实浏览器、真实输入法和读屏验收。

06 / BUILD YOUR OWN

实现重点：保护输入，比生成一句聪明的话更难。

建议架构 主回答完成后，独立服务生成一个候选，可返回空。预测默认无工具、无检索、无执行；主回答和用户输入都不等待它。后端验证之后，客户端再检查请求快照是否仍匹配。

四项不可省略的工程措施

  1. Ghost 与真实草稿分层：建议存在单独状态中，未接受前不写 value、不持久化为用户草稿。
  2. 输入优先：输入、粘贴、IME、附件、语音等变化立即清预测；清空后默认不反复弹同一轮。
  3. 代次与快照双校验：线程、最后完成轮次、上下文、输入、权限、策略版本都要检查。
  4. 失败隔离：超时、空结果、拒绝或服务失败只隐藏建议，不妨碍主会话。

缓存必须分清三件事

配置缓存：存 Prompt 版本与策略；预测结果缓存：存当前轮次候选；API Prompt Caching：复用相同输入前缀的计算。

后者能减少重复输入处理，不等于缓存固定追问，也不替代权限和过期校验。稳定指令在前、变化对话在后是可用策略，命中与成本仍需测量。[O5]

查看防止晚到结果覆盖草稿的核心伪代码
let epoch = 0;
let pending = null;

function invalidate() {
  epoch++;
  pending?.abort();
  pending = null;
  clearGhost();
}

async function predictNextMessage() {
  if (!canRequest()) return;
  invalidate();
  const mine = epoch;
  const key = snapshotKey(); // tenant/user/thread/turn/context/input/permission/policy
  const ctl = new AbortController();
  pending = ctl;
  try {
    const result = await predict(scopedContext(), ctl.signal);
    if (mine !== epoch || key !== snapshotKey()) return;
    if (!inputIsEmpty() || isComposing() || !canDisplay()) return;
    if (!validateGroundingAndScope(result)) return;
    renderGhost(result.prompt); // 仍不写入用户草稿
  } finally {
    if (mine === epoch) pending = null;
  }
}
// 生产代码另处理异常/拒绝/超时；onInput、换线程、新轮次、权限变更都 invalidate。
// 接受只写草稿；正常发送入口单独处理。

这是独立参考方案，不是提取出的客户端代码。取消只是尽力节省工作，返回结果仍须再次比对版本。公开 API 的后台取消与同步断开连接有不同机制，不宜把“取消”理解为保证零费用。[O6]

键盘与无障碍：保留无建议时的正常焦点导航；提供显式采用按钮，避免用户必须使用 Tab；建议只通知一次，不逐字朗读；不抢焦点；支持高对比和缩放。当前本机灰字被标为 aria-hidden，只能说明该装饰层对读屏隐藏，不能据此断言整个产品没有其他辅助通知。

别混淆名称：OpenAI API 的 Predicted Outputs 是开发者预先提供大部分已知输出、加速小改内容的能力。它与“预测用户下一条消息”解决的问题不同，也不是复用这个交互的必需参数。[O7]

07 / MEASURE THE RIGHT OUTCOME

不要把“采纳率”当作最终目标。

本机可见 埋点已经区分生成、放弃、展示、接受、实际发送及是否编辑。评测建议 自有产品应进一步测任务完成质量与目标偏移。埋点存在并不证明原厂就是按以下指标优化。

任务是否完成完成时间、结果可用性、真实缺口是否减少、主观有用性。
用户是否受干扰输入被覆盖、IME 冲突、过期建议闪现、误接受、立即撤销。
是否越带越偏重复工作、原目标偏离、事实被放大、被迫继续无价值对话。
事件与分母能回答什么不能直接推出什么
有效返回 / 预测请求产出覆盖、空结果和失败更多返回就更好；空结果都算失败
接受 / 实际展示有多少展示被转成草稿用户真正想发；任务价值已实现
发送 / 接受接受后有多少被真正发出发送即准确；修改即失败
任务结果 / 随机分组用户配合随机实验评估整体增量建议使用者和未使用者的观察差异就是因果收益
上线前最低验收场景
  • 请求中开始中文输入，预测随后返回。
  • A轮预测晚于B轮回答返回。
  • 切换线程或账号后旧请求返回。
  • 灰字出现时粘贴、录音、拖入附件。
  • 接受后可编辑、清空，旧建议不反复出现。
  • 空输入按Enter先接受，不直接发灰字。
  • 权限撤销／上下文删除后缓存失效。
  • 超时与服务失败不影响主输入。
  • 键盘导航、读屏、缩放与高对比可用。
  • 目标完成、依据不足、需用户选择时不展示。
08 / APPLY TO ADVISORY PRODUCTS

若用于且慢：先验证“理解与服务完成”，再谈增长。

产品建议，非现有功能事实 可优先试点数据口径解释、风险信息补全、已有服务任务接续。每条建议必须保留原目标与证据限制；不从历史涨幅、焦虑或一次点击推断交易意愿和授权。

上下文可尝试的草稿方向判定标准
看完历史数据解释说明这组数据的时间、费用口径和适用限制。理解是否更准确，是否减少误解
用户已提供资金期限结合我已提供的信息，整理还需要确认的事项。信息补全质量，避免编造用户画像
