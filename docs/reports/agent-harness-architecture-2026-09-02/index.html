00 / EXECUTIVE

先给结论：两者不是同一种“好”

DeepSeek Harness 试图把 Harness 变成可重组的元框架；Codex Harness 试图把 Harness 变成可靠、多端一致、可治理的产品控制面。前者更像“智能体 Linux 内核实验场”，后者更像“企业级 Agent Runtime + App Server”。

01

DeepSeek 的真正创新在 Cordis

插件不是外围扩展，而是模型、工具、会话、循环、沙箱、存储、UI 的共同组织方式；服务依赖、事件与可逆副作用由同一上下文内核管理。[S1]

02

Codex 的护城河在控制面

Codex Core 管代理循环；App Server 用双向 JSON-RPC 暴露 Thread / Turn / Item，把 CLI、IDE、桌面和云端统一到同一事件协议。[S7]

03

Harness 决定模型能否长期工作

同一模型放进不同 Harness，会因工具定义、上下文压缩、权限、错误恢复和验证闭环而产生完全不同的完成率、成本与风险。

04

DeepSeek 现在不该直接生产化

项目仍是 developer preview，并明确声明未完成安全审计、不能视为生产就绪；接口破坏性变化也在预期内。[S5]

05

Codex 也不是“万能中立内核”

它开放源码，但最优路径深度耦合 Responses API、模型指令、服务端压缩与 OpenAI 推理内容；跨模型自由度低于 OpenCode/DSH。

06

最佳企业解是“组合借鉴”

拿 DSH 的 capability seam，拿 Codex 的 Thread/Turn/Item 与 App Server，拿 Claude/Gemini 的 hooks 与分层策略，执行面用容器或 microVM。

一句话建议

要快速把 OpenAI 代理能力嵌入产品：优先 Codex App Server；要研发自有、多模型、可热插拔 Harness：借鉴 DeepSeek Cordis，但重写安全与稳定性边界；要在金融企业真正上线：必须自持策略、审计、身份、密钥和执行隔离控制面。

02 / CORE DUEL

DeepSeek Harness vs Codex Harness

一边把“变化”当首要问题，一边把“可靠运行与多端协议”当首要问题。两者都事件化，但事件的职责不同。

DeepSeek Harness

COMPOSABLE META-RUNTIME
Everything is a plugin.
没有特权核心，运行体是一棵可配置插件树。
01
Cordis Context服务仓库 + 依赖注入 + typed events + 可逆 effects；组件卸载时副作用可回收。
02
Profile / Bundle / Patchweb、headless、sdk、minimal、ACP 均是有序组合；可用 overlay 替换任意行。
03
Append-only SessionEvent模型可见内容必须可由日志重建；resume、fork、search、replay 共用事件流。
04
Capability SeamDefinition / Provider / Consumer 三角色；filesystem、subprocess、sandbox、LLM 均可换后端。
05
PTC Code Mode模型生成 TypeScript 程序，通过受控异步 bindings 编排多轮工具调用，降低往返。
06
多代理可跨 Harness同一 subagent seam 可接 in-process、ACP、Codex、Claude Code 或 DSH SDK。
最大风险：插件化把因果链分散到服务、事件、配置层；错误可来自“组合”而非单模块。官方声明目前未经安全审计、非生产就绪。

Codex Harness

PRODUCT CONTROL PLANE
One core, many surfaces.
核心循环集中，外部通过稳定事件协议驱动。
01
Codex CoreRust 核心承载 prompt 构建、模型调用、工具执行、会话持久化、压缩与策略。
02
App Server双向 JSON-RPC；stdio / WebSocket / Unix socket；客户端发请求，服务端持续推 items。
03
Thread / Turn / Item线程持久化、turn 是一次工作、item 有 started / delta / completed 生命周期。
04
Stateless Responses Loop完整前缀随请求重放以支持 ZDR，并依赖精确前缀缓存优化成本。
05
Sandbox + Approval + Rules技术隔离、授权策略、规则与 managed config 分层，工具事件进入 agent-native telemetry。
06
产品面一致CLI、IDE、桌面、Web/Cloud 共用核心逻辑；App Server 将内部事件投影为 UI-ready 通知。
最大约束：最佳能力与 Responses API / OpenAI 模型协同紧密；codex-core 体量持续膨胀，官方仓库指引也明确提醒避免继续把新能力塞进 core。
03 / RUNTIME

一轮任务，实际上穿过 7 个控制点

真正可靠的循环不是“调用模型直到不再调用工具”，而是在每一轮都保持可恢复、可取消、可审计和权限单调。

01 · CLAIM接收与归并输入用户消息、排队消息、subagent mailbox、延迟注入；确定 turn 边界。
→
02 · ASSEMBLE构造上下文系统指令、项目规则、工具 schema、技能目录、权限与环境快照。
→
03 · INFER模型流式推理token 流、reasoning、tool call、最终消息；设置预算、重试和取消。
→
04 · POLICY工具策略判定schema 校验 → allow/ask/deny → 审批 → 参数重写或拒绝。
→
05 · EXECUTE隔离执行工作区、网络、secret、进程树、超时、后台任务；捕获结构化结果。
→
06 · COMMIT记录事实call/result、文件 diff、审批决定、usage、错误与 artifact 进入事件流。
→
07 · DECIDE继续或停止工具是否仍欠下一次请求？是否满足验收？否则进入下一 step 或结束 turn。
turn/startstep/startassistant/chunk*tool/call*tool/result*step/endturn/end

DeepSeek 将这些点作为 durable session events 与 live waterfalls 分开；Codex 将内部低层事件通过 App Server 投影成稳定的 Item 生命周期。两种做法都正确：前者利于内核扩展，后者利于客户端兼容。

05 / MECHANICS

机制下钻：真正拉开差距的 8 个细节

平台宣传页常把工具数量当能力；工程上更重要的是边界、恢复和上下文成本。

CTX

上下文构建：稳定前缀是一等资产

Codex 把 permissions、AGENTS.md、skills metadata、environment context 作为有顺序的输入；中途变化通过追加新消息表达，避免改写前缀破坏缓存。[S6]

  • 规则文档应做“地图”，不是 1,000 页总手册。
  • 工具 schema 要稳定排序；MCP 动态变化会制造 cache miss。
  • 工具目录应懒加载，完整 schema 按需注入。
LOG

事件溯源：事实与模型视图必须分离

DSH 的 session log 是事实源，但并非所有事件都进入模型表面；审批 audit 是 log-only，压缩通过 surface replacement 投影。这个分离非常适合合规审计。

  • 事实日志不可变，模型上下文是可重建投影。
  • UI、检索、fork、telemetry 都从同一流派生。
  • 不要只保存最终 prompt；它不足以解释上下文来自哪里。
POL

工具策略：审批不是安全边界

审批回答“这一次是否允许”；沙箱回答“即使模型犯错，最多能做什么”。两者必须独立。MCP 工具通常不自动继承 shell 沙箱，应自行治理。[S6]

  • 校验 → 静态规则 → 风险分类 → 人/机器审批 → 沙箱执行。
  • 权限只能单调放宽一次，不应悄悄修改全局策略。
  • 无审批回答器、沙箱不可用时，高风险动作必须 fail closed。
CMP

压缩：摘要不是日志，日志也不是上下文

Codex 用 Responses compact 产出可继续的紧凑项；DSH 把压缩做成可替换 seam，并保留压缩范围、shadowed seq、token 计量和调用包络。

  • 先 prune 超大工具结果，再总结旧区间。
  • 不得切断 tool-call / tool-result 配对。
  • 持久规则必须每轮重注入，不能寄望摘要永不丢失。
SUB

多代理：关键不是“能 spawn”

成熟设计至少要回答：子代理是 fresh 还是 fork？工具/权限如何继承？写路径会不会冲突？谁能取消？结果如何回主线程？

  • 只读研究：fresh context + 最小工具。
  • 并行改码：独立 worktree 或声明写域。
  • 长期协作：task DAG + mailbox + revision/CAS + 预算。
PTC

Code Mode：把多轮工具编排压进一个程序

DSH PTC 让模型写 TypeScript 调用 host-provided async bindings；优势是批量、循环和并发，风险是把更多控制流交给模型生成代码。

  • runtime isolation 标签不等于安全证明。
  • bindings 需要 lossless JSON、预算、取消、输出上限。
  • 程序失败应是结构化结果，不应吞掉调用轨迹。
OBS

验收：200、构建成功、页面正确是三件事

DSH 官方复盘记录过 agent 验证了替代服务器而非用户正在使用的 GUI；这类错误本质是“验收目标身份不可见”。[S4]

  • 让 agent 看见当前 URL、进程、版本、环境和 artifact id。
  • 验证真实目标，而非自己另起一个替代环境。
  • 证据需覆盖外部状态，不是只看命令 exit code。
EXT

扩展：表面统一与内核统一有本质差别

Claude/Copilot 的 Plugin 是技能、agent、hook、MCP 等资产包；DSH 的 Plugin 还能替换会话、循环与存储。前者偏分发，后者偏运行时组合。

  • 企业资产包：用 plugin。
  • 跨系统实时能力：用 MCP。
  • 可复用流程知识：用 skill。
  • 机械强制与审计：用 hook / policy。

type AgentEvent =
  | { type: "turn.started"; threadId; turnId; inputRef }
  | { type: "context.assembled"; sourceRefs[]; toolCatalogHash; policyHash }
  | { type: "model.requested"; provider; model; cacheKey; tokenEstimate }
  | { type: "tool.proposed"; callId; tool; argsHash; risk }
  | { type: "approval.decided"; callId; actor; decision; scope }
  | { type: "tool.completed"; callId; resultRef; sideEffects[] }
  | { type: "artifact.verified"; target; evidenceRefs[]; verdict }
  | { type: "turn.completed"; outcome; usage; finalMessageRef }

// 原则：事实 append-only；大内容存 blob，事件只存 hash/ref；模型视图由 projector 重建。
while (turn.hasDebt()) {
  input = inbox.claimOneWakeupAndQueuedMessages()
  view  = context.project(sessionLog, policySnapshot, skillCatalog)
  step  = model.stream(view, tools.schemas(), budget.signal)

  for (call of step.toolCalls) {
    validated = tools.validate(call)
    decision  = policy.evaluate(validated, identity, environment)
    grant     = decision.ask ? approvals.resolve(decision) : decision
    result    = grant.allowed
      ? sandbox.execute(validated, grant.scope)
      : ToolResult.denied(grant.reason)
    sessionLog.append(call, grant.audit, result)
  }

  acceptance.observe(step, artifacts, externalState)
}
return turn.complete()

09 / BENCHMARK

评测方法：同模型只是起点，真实完成闭环才是终点

不能拿不同平台的官方 benchmark 横拼。正确方法是固定模型、仓库快照、权限、任务与验收器，分别测 Harness 增益与总产品效果。

两层对照实验

Harness-only同模型 / 同 task / 同工具
Product-total各平台最佳模型与默认配置
主指标可复现任务成功率
次指标人工中断、时间、token、成本
安全指标越权/泄露/误写/审批绕过
恢复指标断线、压缩、重启、fork 后一致性
证据指标外部验收覆盖率与 replay 完整度

最终架构判断

DeepSeek Harness 提供了 2026 年最有野心的“可组合 Harness 内核”范式；Codex Harness 提供了更成熟的“Agent 产品控制面”范式。前者告诉你系统如何被替换，后者告诉你系统如何被使用、治理和跨端承载。金融企业应把两者结合，但安全执行、身份授权和审计证据必须自己掌握。

今天可用Codex / Claude / Cursor / Copilot 承载日常研发与交付
现在该试用 DSH 搭一个隔离实验场，验证 plugin seam 与 replay
必须自建金融 MCP gateway、purpose-bound auth、审计与验收控制面
