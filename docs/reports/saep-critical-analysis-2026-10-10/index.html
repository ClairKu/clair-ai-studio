Critical protocol review · 2026-10-10

SAEP不是“万能操作协议”

它是豆包手机助手体系中，面向外部 GUI 自动化的应用侧治理接口。它试图回答“智能体能不能看、能不能点、哪些意图必须拦、出了事去哪查”，却没有完整回答“谁授权、授权给谁、这一步是否被篡改、结果由谁担责”。

01 / 一句话定性

SAEP 是“门禁与摄像头”，不是“道路与车辆”

GUI 是智能体跨应用行动的通道；SAEP 是这条通道上的准入、禁止与留痕机制；MCP / AppFunctions / App Intents / 小程序 Skill 是结构化能力接口；A2A 是不同智能体之间的协作语言。把它们混称为“Agent 协议”，会把完全不同的责任层揉成一团。

01

有价值

首次把 App 的拒绝权、截图与输入控制、意图限制、Agent 身份查看和本地审计放进同一治理面。

02

不完整

公开材料仍是 Demo 与平台集成面，不是经过多方实现、正式治理、互操作测试的成熟开放标准。

03

有偏向

它强化 App 对外部 Agent 的否决权，也可能被用于安全保护、商业护城河或流量封锁，三者并不天然等价。

04

方向正确

终局不会是纯 GUI 或纯 API，而是“结构化能力优先、低风险 GUI 兜底、高风险回到目标 App 确认”。

最重要的事实边界：截至本报告截点，没有可靠公开证据证明微信、小微或腾讯采用了 SAEP；微信 AI 生态参与者也不能被称为“SAEP 用户”。二者是竞争又可能互操作的两套路线。
02 / 协议全景

手机 Agent 的六层栈

① 意图与规划大模型理解用户目标、拆解任务、选择路径模型 / Planner
② Agent 协作一个 Agent 发现、委托和跟踪另一个 Agent 的任务A2A
③ 工具与能力以类型化参数调用服务，而不是猜屏幕位置MCP · AppFunctions · App Intents · 小程序 MCP/Skill
④ GUI 执行识别屏幕并点击、输入、滚动，是兼容存量应用的最后一公里Computer Use · UI Agent
⑤ 策略与授权App、系统、用户共同决定是否允许看、点、改、发、删SAEP · OAuth/OIDC · 本地授权
⑥ 业务权威与凭证支付、发帖、删除、开户等结果必须由目标系统确认并出具回执订单 / 交易 / 审计账本
关键纠偏：SAEP 只覆盖第⑤层的一部分，并约束第④层。它不负责模型是否聪明，不定义工具语义，也不替代支付、消息或账户系统的业务授权。
框架解决什么典型对象不解决什么
SAEP外部屏幕自动化的限制、Agent 查询与本地审计OS / App / GUI Agent工具标准、Agent 协作、业务授权
MCP模型或 Agent 发现并调用工具、资源、提示AI 客户端 ↔ 工具服务器跨 App GUI 门禁、Agent-to-Agent 生命周期

GUI 的优势

覆盖不提供 API 的存量应用；不等开发者逐一改造；视觉路径与人类操作一致，快速跨越“最后一公里”。

GUI 的结构性缺陷

页面改版即失效；模型可能点错对象；弹窗、遮罩、WebView 与异步状态造成歧义；屏幕内容可实施提示注入。

SAEP 能做的

从系统侧硬控截图与输入，从应用侧声明范围，从意图层限制修改、发布、删除与激励行为，并提供事后查询入口。

最佳执行阶梯：只打开 App → 只读界面 → 受 SAEP 约束的低风险 GUI → 类型化接口 → 目标 App 内确认与结果回执。风险越高，越不应靠“看着像对了”的像素操作完成。
04 / 与微信小微的关系

不是同一协议：一个守外门，一个建内城

SAEP 路线：OS 级外部 Agent

豆包手机助手站在操作系统与多 App 之上。遇到没有结构化能力的 App，就需要通过 GUI 观察与操作；SAEP 用来决定这种外部自动化能走到哪里。

跨 AppGUI 兜底App 可拒绝

小微路线：微信内生 Agent

小微在微信内部拥有原生能力，并通过微信 AI 生态调度小程序。自动模式由平台解析页面与源码；开发模式把业务抽象为 Skill、原子接口和原子组件，由小程序 MCP 选择执行。

超级 App 内结构化能力平台审核
场景实际执行路径SAEP 是否关键真正的控制点
小微发送微信消息、发起通话或调整微信设置微信内部原生能力通常不是微信自身权限、风控与用户确认
小微调用外卖、旅行、购物等小程序服务小程序自动模式或 Skill / 小程序 MCP主要不是小程序授权、原子接口、支付和身份确认
豆包等外部手机 Agent 操作微信界面跨 App GUI 自动化可能是前提是微信选择声明 SAEP 策略；目前无公开采用证据
小微未来调用微信之外的独立 AgentAgent 协作或平台私有编排间接相关A2A、MCP、OAuth 与业务授权更关键

真正的竞争不是“谁的模型更会点”，而是谁成为用户意图的总入口：OS Agent 想跨越所有 App，超级 App Agent 想把服务留在自己的生态内。SAEP 把外部 Agent 的权力交回 App；微信 AI 则把小程序能力重新封装为可被内部 Agent 调度的服务。

06 / 公开实现解剖

SAEP 目前到底定义了什么

策略文件

AGRP-Policy/1.0，绑定 App 包名，包含版本与更新时间；静态策略放在 Manifest 元数据，动态策略经系统 Provider 更新，最大 10 KiB。

三级范围

默认策略、应用范围、Activity 页面范围。可禁止全部操作、截图或输入；页面以 Android Activity 名称表示。

四类意图

修改内容、发布内容、删除内容、账户激励。官方同时承认：大模型意图识别有不确定性，无法保证每次都正确拦截。

Agent 身份

App 可列出设备上登记的可信 Agent UUID，并查询某个 Agent 的详情。

本地审计

App 可按时间、目标意图和 Activity 查询自己的操作历史；示例最多展示 100 条并限制输出大小。

系统依赖

依赖私有的 android.security.obric.* Stub 与 com.obric.agentrobots.provider，不是普通 Android 公共 SDK。

07 / 批判性审视

七个问题，比“有没有协议”更重要

1. 它是标准，还是平台规则？

公开仓库是示例工程，核心运行时是私有系统接口。没有独立标准组织、规范性 RFC、多厂商参考实现和互操作认证，就不能与成熟开放标准画等号。

2. App 拒绝权会不会压过用户委托权？

保护支付与隐私合理；但若 App 以安全为名阻止比价、屏蔽迁移、强留广告或阻断竞争服务，SAEP 也可能成为平台封锁工具。政策必须有理由码、透明度与申诉机制。

3. 负面布尔值太粗

“禁截图 / 禁输入 / 禁四类意图”无法表达一次性授权、金额上限、对象白名单、时间窗、撤销、条件确认和敏感字段脱敏。真实授权应是任务绑定的能力票据。

4. Activity 不是稳定页面语义

现代 App 常用单 Activity、Compose、WebView 和动态组件。用 Activity 名称代表业务页面，粒度可能过粗，也难覆盖同屏不同控件的风险差异。

5. UUID 不等于可信身份

知道 Agent 的 UUID，不代表验证了发布者、代码完整性、当前模型版本、代理链条或用户授权范围。需要硬件证明、签名身份与任务级委托凭证。

6. 有日志不等于可追责

本地可查询记录不天然具备防篡改、跨方对账与不可否认性。关键操作应记录任务 ID、策略版本、授权快照、模型／工具版本、输入输出摘要和目标系统回执。

7. 意图分类器本身会错

同一个“点击”可能是浏览，也可能是下单；同一句“帮我处理”可能跨越多个风险等级。官方已明确无法保证所有操作都被正确识别和拦截，不能把语义风控当硬边界。

真正的攻击面

屏幕提示注入、误触确认、遮罩欺骗、状态漂移、跨 App 拼接权限、账户切换、重放、策略降级与日志缺口，均不是四个意图开关能独立解决的。

最尖锐的判断：SAEP 当前更像“平台治理创新”，还不是“完整安全协议”。它解决了 App 没有表达拒绝权的问题，却尚未建立用户、Agent、系统、App 四方之间可验证的权责契约。

08 / 更优解

SAEP 2.0 应从“开关”升级为“任务契约”

签名策略

策略必须签名，含生效期、过期时间、回滚保护、发布者与可解释理由码。

任务级授权

把用户、Agent、目标 App、动作、对象、金额、时间窗与一次性 nonce 绑定为不可重放的授权票据。

稳定语义 ID

为敏感页面、控件和业务意图提供稳定标识，不把治理边界绑死在 Activity 或像素位置。

风险类型化

读、写、发布、删除之外，增加支付、账户、身份、健康、法律、设备控制与不可逆操作。

可验证回执

目标 App 对最终业务状态签发回执；跨方日志具备哈希链、时钟与最小必要披露。

开放治理

独立规范、测试套件、红队用例、多厂商实现、版本兼容政策、透明度报告与申诉机制缺一不可。

风险等级允许的执行方式最低保障示例
L0 导航GUI 或深链可撤销、无数据变更打开 App、进入页面
L1 读取受控 GUI / 类型化查询字段脱敏、目的限制查看天气、订单状态
L2 低风险写入SAEP 约束 GUI 或工具调用预览、撤销、完整日志填写草稿、调整非敏感设置
L3 对外发布／删除类型化接口优先明确对象、内容预览、二次确认发消息、发帖、删内容
L4 钱与身份目标 App 原生流程强认证、交易绑定、签名回执支付、开户、转账、健康／法律操作
产品决策建议：不要押注“纯 GUI 能操作一切”。建设“结构化能力目录 + GUI 兜底 + 风险分级 + 人工确认 + 业务回执”的混合架构；接入方优先暴露高频、低风险、可撤销的原子能力，高风险行为永远回到权威系统完成。
