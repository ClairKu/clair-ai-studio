# Clair Review OS｜产品与设计智能评审器

更新日：2026-08-06

## 1. 要解决的真实问题

Clair 每天需要重复指出大量基础产品与设计问题：目标不清、场景缺失、范围模糊、只写正常路径、状态与异常遗漏、按钮层级不符合决策优先级、交易与投顾语义混用、风险提示与授权留痕不完整、原型与 PRD 不一致。现有做法把高级产品判断消耗在低杠杆重复劳动中，也没有把每次评审转化为团队可复用的质量系统。

评审器的目标不是替 Clair 生成一份泛化清单，而是逐步形成一套可以解释、纠正、回归和发布的个人评审操作系统：

1. 自动识别材料中的问题，并定位到原文或画面。
2. 按 P0 / P1 / P2 说明问题、影响和可执行改法。
3. 生成可直接发给 PM / 设计师的评审结果。
4. Clair 可以逐条编辑、补充或否定自动结论。
5. 修改差异形成优化候选，经人工确认后更新下一版规则。
6. 可持续加入正例、反例和边界例，用相似案例增强后续判断。

## 2. 四层评审模型

### L1 通用高级产品原则

- 问题先于功能；目标必须对应明确用户、触发场景与可验证结果。
- 范围必须有本期边界、非目标和取舍。
- 规则必须覆盖输入、判断、输出、权限、状态机、异常与回退。
- 交互层级必须服务用户决策，不用视觉强调掩盖产品逻辑缺失。
- 指标分为成功指标、护栏指标和诊断指标，并明确基线、目标、口径和 Owner。
- 验收标准必须可观察、可测试，核心规则至少覆盖正常、权限/资格、异常和追溯路径。

### L2 且慢 / 盈米业务红线

- 明确区分自主交易、投顾跟投、策略调仓、定制账户、单基金买入和 AI 解释/建议。
- 任何授权、适当性、风险披露、推荐或交易含义都必须可留痕、可查询、可投诉追溯。
- AI 必须区分确定性业务规则与生成式内容，定义来源、边界、禁区、失败兜底和人工复核点。
- 新方案要先对照且慢现有能力、术语、数据服务和用户路径，避免重复与冲突。

### L3 Clair 个人原则

系统把 Clair 的修改拆为四类：新增原则、权重变化、例外条件、表达方式。单次修改不会直接覆盖模型，而是进入候选队列；相同模式重复出现或 Clair 主动确认后才发布新版本。

### L4 案例库

每个案例保存：原材料、自动评审、Clair 最终意见、最终改稿、是否采纳、适用范围、例外条件、来源与日期。案例分为：

- 正例：什么情况下可以通过，以及为什么。
- 反例：重复出现的产品/设计反模式。
- 边界例：某条原则何时不适用，防止过度泛化。

评审时先做规则检查，再检索相似案例作为判断证据；案例只辅助决策，不替代业务事实。

## 3. 受控进化闭环

`材料 → 自动评审 → Clair 修改 → 差异提炼 → 优化候选 → 案例回归 → Clair 批准 → 新版本 → 可回滚`

必须保留原始材料、原始输出、人工修改、采用理由、版本与时间。候选版本至少通过历史成功案例、边界案例和失败案例；模型发布必须由 Clair 确认。

## 4. 本次可用 MVP

- 文本 / PRD 本地规则扫描：真实运行，不上传材料。
- 原文高亮定位、P0 / P1 / P2 分级、问题—影响—改法。
- 逐条编辑评审意见、复制 PM 版、导出 Markdown。
- 图片上传与画面点选标注。
- 原则库、案例库、进化候选、版本发布与本地持久化。
- 相似案例提示与“本次评审沉淀为案例”。

## 5. 证据与能力边界

当前发布形态是 GitHub Pages 静态应用。文本扫描采用确定性本地规则；案例、个人原则和修改记录保存在当前浏览器 `localStorage`，不是跨设备数据库。上传图片仅在当前浏览器显示并支持人工点选标注；未接入多模态服务前，不宣称已经自动理解任意设计稿。

生产级下一阶段需要：

1. 接入公司 OAP / Codex 多模态评审服务，并通过服务端保存密钥。
2. 接入受权限保护的案例库、原则库与版本库，支持跨设备和团队协作。
3. 对 Figma frame、PRD、原型和视觉稿做多材料一致性比对。
4. 建立历史案例回归集、评审命中率、误报率、人工修改率和 PM 采纳率指标。
5. 对涉及投资建议、交易、用户数据的材料建立访问控制、审计和保留策略。

## 6. 成功标准

- 重复基础问题由系统首轮覆盖，Clair 主要处理高阶取舍与例外。
- 自动评审结果可直接发送比例持续提高。
- 同类问题人工重复补充率下降。
- 每次模型发布都有可解释差异、回归结果和回滚点。
- 案例库不仅增加数量，还能降低误报并改善边界判断。
