# OAP 报告协作复盘｜研究源

## 范围

- 复盘对象：2026-08-02 至 2026-08-03，共同完成的盈米 AI 开放平台（OAP）管理汇报及其 CLAIR 视觉报告发布任务。
- 复盘截止：2026-08-04。
- 事实边界：以历史任务记录、结构化报告资产、构建/发布记录为依据；屏幕观察只用于解释协作过程，不作为当前线上状态证明。
- 公开边界：不包含内部账号、个人联系方式、未落地合作细节和敏感业务明细。

## 一句话判断

这次真正完成的不是一份“好看的报告”，而是把分散材料、多版本改动和模糊进度，收敛为一个证据可追溯、管理层可决策、工程上可发布、方法上可复用的报告生产系统。

## 已确认成果

1. 从飞书 Wiki 最新 revision 1978 审计增量，区分 confirmed / inferred / missing / target。
2. 将并行版本中的微信场景、能力生产线、用户共创、服务蓝图、机构使用、MCP TOP20、商业化收费路由等有效改动合并。
3. 最终发布版包含 22 章、9 项来源，基于干净主线重建并以 commit fa71012 发布。
4. 完成构建、测试、差异检查、桌面端与 390px 移动端检查，并验证 GitHub Pages 生产内容和工作台入口。
5. 把一次性视觉样式抽象为 `report.json + 模板 + 校验器 + 发布质量门` 的 CLAIR 报告工作流。

## 做对的事

### 1. 先审证据，再写结论

没有直接从材料中“挑亮点”，而是先比较来源版本、核对指标口径、标注事实状态，避免把规划、邀测、待上架或推断写成已落地成果。

### 2. 保留源框架，再补管理问题

报告保留飞书原始结构和覆盖范围，同时补齐管理层真正关心的决策信息：能力如何进入业务闭环、商业化门槛、治理责任、风险、不确定性和下一步动作。

### 3. 内容与视觉分层

用 `report.json` 管内容和证据，用模板管理视觉、导航、响应式和交互。这样内容变化不再要求重写整页，也使模板能够复用于下一份材料。

### 4. 把发布当成交付的一部分

`git push` 不是完成。完成定义包括：构建与测试通过、Pages 成功、线上 HTML/标题/资源可访问、工作台唯一入口存在、桌面与手机无溢出。

### 5. 把用户纠偏变成规则

“最新最完整”被翻译成跨版本有效改动的并集；“忽略最后一次指令”被翻译成只撤回指定变化；“由下至上”被翻译成明确的服务关系信息架构。这些都沉淀成了可复用约束。

## 绕路与根因

### 1. 多个工作副本并行演进

不同副本分别包含互补改动，且部分处于 rebase/cherry-pick 冲突状态。根因不是 Git 技术问题，而是缺少发布基线、变更账本和唯一集成分支。

### 2. 过早进入视觉微调

标题裁切、页面高度、关系图方向等问题被反复修正。部分返工来自内容骨架、模块数量和关键关系尚未冻结时就开始精修视觉。

### 3. “能打开”与“受保护”混在一起

一键开启改善了体验，但自动解锁材料等同于向持有公开链接的人授予访问，不应被描述为真正的访问控制。

### 4. 发布状态容易被误判

远端并发导致 push 被拒、Pages 仍在 building、本地存在未完成 cherry-pick，都说明“本地生成”“已推送”“已上线”“已验证”是四个不同状态。

### 5. 工具异常可能掩盖真实状态

Keychain 未初始化不等于无权限，动态页显示 JavaScript 禁用不等于无数据，截图接口不兼容也不等于页面不可验收。应更快切换到权威读取路径、DOM/尺寸审计和生产页检查。

## 协作层面的经验

- 用户的价值不只是提供材料，而是不断抬高完成标准：从“做报告”推到“完整、最新、能发布、能复用、能回答老板问题”。
- AI 的价值不应停留在执行排版，而要承担证据审计、版本整合、管理叙事、工程发布和质量验证。
- 高效协作需要把口语要求翻译成验收规则，并把每次纠偏沉淀为下一次的默认流程。
- 速度和严谨不冲突。真正拖慢任务的往往不是校验，而是基线不清、版本分叉和完成定义模糊。

## 下一次默认 SOP

1. 建立材料清单与公开边界。
2. 锁定权威版本、截止时间、数据口径和发布基线。
3. 建立来源覆盖表与变更账本。
4. 先形成“结论—证据—决策—行动”骨架，再进入视觉设计。
5. 用结构化 JSON 维护内容，用稳定模板生成页面。
6. 评审只收敛差异，不并行制造多个完整版本。
7. 在干净主线上集成，构建、测试、差异检查。
8. 等待 Pages 成功后验证生产 URL、资源、工作台、桌面和 390px。
9. 发布后记录版本、变更说明、证据缺口和下一次更新入口。

## 更深一层的结论

报告不是项目的“最后一公里包装”，而是迫使团队统一事实、口径、判断、责任和下一步的管理系统。最值得复用的不是某个紫色版式，而是这条闭环：材料可追溯、判断可解释、动作可执行、发布可验证、方法可复制。
